# 第22章：面向金融研究的检索增强生成

大语言模型（LLM）能够综合复杂的金融文档，但也会以极具说服力的流畅口吻编造细节。在金融领域，这种失效模式不是无关痛痒的小毛病，而是部署上的一票否决项。**检索增强生成**（**RAG**）的应对之道，是让每个回答都锚定在一个受控的证据库上——其内容、时间戳与引用都可以直接查验。

本章将金融 RAG 系统作为一套工程技术栈来构建，而非一种提示词技巧。完成本章后，你将能够：

- 解释为什么幻觉使无依据的大模型应用在金融领域不可接受，以及为什么检索增强生成是核心的架构性应对。
- 设计一条从文档摄取到检索与有据生成的金融 RAG 流水线，包括结构感知解析、分块（chunking）、元数据、嵌入与引用支持。
- 比较通用与领域专用嵌入模型，并用实用的检索指标与延迟权衡在目标语料上评估检索质量。
- 构建融合语义检索、词法检索、元数据过滤与重排（rerank）的检索技术栈，以提升金融文档上的精确率与召回率。
- 使用基于约束的提示词、引用校验与工具验证的计算，使生成的回答更忠实、可审计、数值上可靠。
- 通过区分检索、上下文、综合、计算与弃答错误来诊断 RAG 失效，并应用针对性的评估方法改进各组件。
- 区分金融应用中何时使用 RAG、何时使用微调，并解释 RAG 如何作为更广泛的智能体工作流中的一个工具发挥作用。

*22.1–22.2 节* 界定问题与核心架构方案。*22.3–22.6 节* 从文档摄取到提示词与工具验证的计算，逐层搭建这套技术栈。*22.7 节* 引入用于系统性调试 RAG 的评估框架。*22.8 节* 比较实际应用场景与 RAG 和微调之间的战略边界，*22.9 节* 则展示 RAG 如何成为更广泛的智能体工作流中的一个工具。

## 22.1 从特征提取到生成

*第10章* 构建了一套从金融文本中提取结构化特征的工具箱——情感分数、风险类别、特征向量——使用的是 FinBERT（Huang, Wang, and Yang, 2020）等领域适配的 Transformer，以及更早的基于词典的方法，如 Loughran-McDonald 词典（Loughran and McDonald, 2011）。这些输出可以直接喂入交易信号与风险模型，但分类有其天花板。

微调后的 FinBERT 能判断 10-K 文件中的某句话*是否*负面，却无法解释*为什么*。它无法综合不同章节的信息，无法回答多跳问题，也无法生成叙述性摘要。从业者与它的交互被限制在一个固定的分类体系内。而人类分析师的工作是提出这样的问题：*“是什么推动了欧洲分部的营收增长？针对这些业务又提到了哪些风险？”* 判别式分类器回答不了这个问题。

现代大语言模型把从业者的目标从“提取一个特征”转变为“提出一个复杂问题”（Saha et al., 2025）。LLM 建立在 Transformer 架构之上（Vaswani et al., 2017），又经指令微调打磨，天生为*生成*而设计：它们的主要输出是人类可读的内容——摘要、分析、回答——而不是数值特征。

多步综合、上下文学习与指令遵循这些能力，随规模与指令微调而急剧提升（Wei et al., 2023）。在金融领域，LLM 可以凭提示词中的少量示例举一反三，无需领域专用微调即可完成复杂的情感分析（Xie et al., 2024; Lopez-Lira and Tang, 2025）。模型实际上是从上下文中学会了一项新任务，从而能够承担此前只有人类专家才能胜任的分析工作：总结管理层讨论与分析（MD&A）章节、起草投资论点，或从艰深的监管文件中识别风险因素。

这种能力伴随着一个固有缺陷：**幻觉**。LLM 会生成看似合理、语气自信、语法无误但事实错误或完全虚构的输出（Lopez-Lira, Tang, and Zhu, 2025）。幻觉是训练用于预测下一个最可能 token 的概率模型的内在属性，不是可以打补丁修掉的 bug。

在金融领域，这种风险不可接受。一条被虚构的事实——凭空捏造的营收数字、不存在的监管要求、张冠李戴的 CEO 引语——就可能引致错误的投资决策、合规违规或法律责任。近期的金融领域研究记录了一些相邻的失效模式，指向同样的运营教训：LLM 在投资分析中可能表现出系统性偏差，而当记忆污染预测任务时，它可能显得比实际更可靠（Lee et al., 2025; Lopez-Lira, Tang, and Zhu, 2025）。具体的失效形态因任务与评估协议而异，但结论是稳定的：流畅的输出不能自我证明，在高风险场景中，哪怕偶尔出现无依据的断言也不可接受。

事后事实核查无法规模化，也无法触及根因：模型的生成过程是不透明的，纠正一条输出并不会修复底层有缺陷的逻辑。解决方案必须是*架构性*的——用一个框架约束 LLM，使其只能在可信、可验证的信息之上生成。这正是检索增强生成的核心原则。

## 22.2 用检索增强生成锚定大语言模型

**检索增强生成**（RAG）由 Lewis et al. (2020) 首次形式化，它在架构层面应对幻觉问题。RAG 不信任模型的参数化知识（预训练期间编码进权重的信息），而是约束 LLM 依赖*非参数化*知识——一个由系统控制、可以验证的外部知识库。由于生成以检索到的上下文为依据，每一条断言原则上都能回溯到具体的源文档、页面或段落。要在实践中实现可靠的溯源（provenance），还需要 *22.6 节* 讨论的引用校验技术。

### 索引-检索-生成流水线

RAG 系统将信息检索系统与大语言模型结合起来，分三个阶段：

1. **索引（离线）**：这是构建知识库的准备阶段。系统摄取并处理可信文档语料——例如 SEC 申报文件、业绩电话会议记录、研究报告或监管指引——并将其转换为可检索的格式。每份文档被解析并切分为更小、更易管理的文本块（chunk）。每个块随后经过**嵌入模型**，转换为稠密的数值向量表示。这些向量连同对应的文本块和元数据（源文件、页码、章节标题）一起，存入为相似度搜索优化的**向量数据库**。
2. **检索（在线）**：用户提交查询后，检索阶段启动。用户的自然语言问题用与索引阶段相同的模型转换为向量嵌入。随后查询向量数据库，找出向量与查询向量语义最相似的 *k* 个文本块（通常以余弦相似度衡量）。这些 top-*k* 文本块构成检索到的上下文——系统认为与回答问题最相关的一组源材料。
3. **生成（在线）**：在最后阶段，检索到的文本块与原始查询合并为一条完整的提示词。这条增强提示词被发送给 LLM，并附带一条关键指令：**仅基于所提供的上下文综合答案**。这一约束正是强制锚定的架构机制。LLM 被明确告知不要依赖内部知识，而是充当对所给证据的综合引擎。输出是一个生成的回答，理想情况下还带有指向支撑各断言的源文本块的引用。

### 编排层

**LlamaIndex**（为 RAG 流水线优化：摄取、索引、检索）与 **LangChain**（具备模块化链与智能体模式的通用 LLM 应用框架）等框架，抽象掉了连接解析器、嵌入模型、向量数据库与 LLM 的底层管道。两者都是开源项目且迭代迅速；选择取决于工作流是以 RAG 为中心（LlamaIndex），还是更大智能体架构的一部分（LangChain）。**Haystack** 等新入场者也提供了备选方案。

这一范式的简洁既是优势也是局限。采用固定大小分块、通用嵌入模型和朴素向量搜索的直接实现，在金融领域常见的复杂、术语密集的文档上会失效。生产系统在每个阶段都需要进阶技术：结构感知解析、领域专用嵌入、混合检索、重排与基于约束的提示词。后续各节将自底向上搭建这套技术栈。

## 22.3 智能文档摄取

任何 RAG 系统的性能上限都由其知识库的质量决定，而质量始于文档摄取。金融文档——SEC 10-K 与 10-Q 申报文件（其结构见 *第4章*）、业绩电话会议记录、招股说明书与监管指引——冗长而致密，混杂着叙述性文字、表格、内嵌图像与层级结构。朴素的摄取方式会破坏这种结构并拖累检索。

### 朴素分块的失败

最简单的摄取方法是固定大小分块：把文档切成 500 或 1000 字符的块，辅以一定重叠。这种方法计算廉价，但对语义是破坏性的。金融表格——定量数据的关键来源——被任意切碎，列标题与其数值分离。“Item 7. Management's Discussion and Analysis”（第 7 项：管理层讨论与分析）之类的章节标题，与其引领的段落被割裂。风险因素列表项被拆散到不同块中，丢失原有的逻辑分组。

结果就是从业者所说的“上下文混淆”。当检索系统取回这些碎片化的块并交给 LLM 时，模型可能混淆不同财年的信息，把表述错误归入错误的章节，或因必要的上下文散落在互不相关的块中而无法综合出连贯的回答。朴素分块违背了 RAG 的根本前提：检索到的上下文应当为生成提供可靠的锚定。

### 分块大小：根本性权衡

分块大小是 RAG 系统设计中影响最大的超参数之一，得到的关注却相对很少。

约 200–300 token 的*小块*检索精确率更高——系统能精确定位真正相关的句子或段落。但小块缺乏上下文。一句“营收增长 15%”，若不知道属于哪个分部、哪个期间、是内生增长还是并购驱动，就毫无意义。小块迫使检索系统取回许多碎片，再指望 LLM 能正确拼装。

而 1000–2000 token 的*大块*每块上下文更自足，减少了跨块综合的需求。但更大的块会稀释相关性——如果 1500 token 的块中只有一段相关，其嵌入表示的就是相关与无关内容的平均，可能损害检索准确性。大块还会消耗更多 LLM 的上下文窗口。

对金融文档，常见的起点是 400–600 token、重叠 50–100 token，但这些只是默认值，不是普适答案。最优大小取决于文档类型、查询模式与 LLM 的上下文预算。把分块大小当作超参数对待：在评估集上，先在一组网格尺寸（256、512、768、1024）上评估检索召回率，再最终确定。*图 22.2* 对比了固定大小、语义与结构感知三种分块策略，展示了速度与质量之间的权衡。

一种实用的折中是**父文档检索**（Parent Document Retrieval，即“小到大”策略）：用小而精确的块做检索，但把更大的父级章节交给 LLM。每个段落都有自己的嵌入以保证检索精确性；一旦某个段落命中，系统返回完整的子章节。这以摄取时维护“块-父文档”映射为代价，同时兼顾精确匹配与丰富上下文。

### 结构感知解析

解决朴素分块的方案是**结构感知解析**：理解文档语义布局的工具。这些工具不把 PDF 当作字符流，而是识别并保留章节边界、段落分组、表格布局与列表层级。LlamaIndex 开发者推出的 **LlamaParse** 是代表性例子。它结合视觉模型与 LLM，从文档的视觉呈现中智能重建其逻辑结构。表格不是以碎片文本、而是以结构化 Markdown 或 JSON 的形式提取，保留行、列与表头。图表可由视觉模型处理，生成其内容的文字摘要。章节与子章节之间的层级关系被保留，使检索系统能识别出：讨论“欧洲营收”的段落属于“地理分部分析”这一更大的上下文。

IBM 推出的 **Docling** 提供了一个开源替代方案，其混合解析器结合了版面检测、表格识别与文本提取。**Marker** 专注于高保真的 PDF 转 Markdown。工具生态迭代迅速，到本书出版时可能已有更新的选项。稳定不变的原则是结构保留——以此为标准评估工具，而不是忠于某个品牌。

这些工具并非万无一失。扫描版 PDF 需要先用**光学字符识别**（OCR）预处理，可能引入转录错误。版式不规范的文件——嵌套表格、多栏排版、跨页脚注——即使视觉解析器也可能应付不了。以图像而非 HTML 渲染的表格尤其棘手：解析器必须先（通过 OCR）检测再重建表格结构，而这是一条误差不断累积的流水线。在大规模信任解析结果之前，先在代表性文档上验证解析器输出。在金融 RAG 中，摄取错误在下游实际上不可逆：表格、标题或时间标记一旦丢失，后续的检索与生成阶段无法可靠地重建它们。

### 多模态内容：表格、图表与图像

金融文档天然是多模态的。一份 10-K 不仅有叙述性文字，还有财务指标表格、组织架构图、流程图，偶尔还有内嵌图像。忽略这些内容会牺牲大量信息密度。

表格尤为关键——分析师最常查询的定量事实往往就在表格中。结构感知解析器在保留行列关系的前提下，把表格转换为 Markdown 或 JSON。难点在于 PDF 中的表格常常只是视觉渲染、没有底层结构，需要视觉模型重建其逻辑布局。

图表可能包含周围文字没有的信息——例如，分部营收柱状图可能是唯一出现各分部增速的地方。闭源与开放权重的视觉语言模型都能生成文字描述，与正文一起被索引。代价不可忽视：摄取阶段每张图像都需要一次视觉模型 API 调用，增加延迟与费用。一条实用的启发式规则：表格一律处理（信息密度高、输出结构化）；图表只在包含正文未重复的定量数据时选择性处理。

一种新兴方案完全绕开文本提取：ColPali（Faysse et al., 2025）等**视觉优先检索**模型把文档页面作为图像索引，用视觉语言嵌入进行检索。这规避了解析错误，但牺牲了金融 RAG 依赖的结构化元数据——章节层级、报表类型、财年期间——而这些正是过滤检索与可验证引用的基础。文本提取流水线仍是生产默认选择；视觉优先方案值得在模型成熟过程中持续关注。

### 元数据：可验证引用的关键

除内容解析外，摄取阶段还必须为每个块打上丰富的**元数据**。至少包括：源文档名、页码与章节标题（例如“Item 1A. Risk Factors”，风险因素）。对金融文档而言，**时间元数据至关重要**：财年、财季、申报日期与期末日期。查询“苹果 2023 年的风险因素”绝不能取回 2022 年的披露；询问“最新指引”则必须优先返回最新申报。

没有显式的时间标记，检索系统无法区分当前信息与过时信息——在金融领域这是特别危险的失效模式，过时的数据可能比没有数据更糟。除财年与财季外，摄取还应跟踪申报公开日期、所指的财务期间与摄取时间戳，以保障**时点完整性**（point-in-time integrity）。这些字段不可互换：2024 财年期间的披露可能到 2025 年才公开。历史查询与回测必须按公开可得时间过滤，而不能只看期间标签，以防信息泄露。

每个索引单元还应包含足以支撑后续引用校验的溯源信息，即其结构角色（叙述性文字、表格单元格、脚注、图题）与提取方式。缺少这种感知模态的元数据，引用格式可能看起来很精确，却仍无法实现断言-证据对齐。

元数据有两个用途：

1. 支持过滤检索：用户查询“苹果 2023 年的风险因素”时，系统可以自动把搜索限制在打了正确公司与财年标签的块上，提高精确率。
2. 支持可验证引用：LLM 生成回答时，可以附上页码与章节引用，让分析师直接跳到源头核实信息——闭合任何高风险金融应用都必需的信任回路。

对生产级金融 RAG 而言，元数据标注不是可选项。摄取质量决定了可供嵌入的语义单元，而嵌入——下一节讨论——决定了检索能找到什么。

**实现**：`01_sec_filing_pipeline.py` 演示了五家 SP100 发行人的端到端摄取流水线：它通过 `edgartools` 解析股票代码，约 2.6 秒内列出十份目标 10-K 申报（每条记录都带申报日期与受理编号），然后运行一次并行的解析器对比，量化结构感知带来的提升：表格保留率约翻倍（0.45 → 0.85），版面保真度接近翻倍（0.40 → 0.88），解析延迟增加约 70%——正是本节定性勾勒的成本-保真度包络。

notebook 还报告了一次元数据完整性审计：在 `edgartools` 的列表对象上，申报日期与摄取时间戳的填充率为 100%，而 `fiscal_year_end` 缺失、必须在下游从文档正文中补充——印证了上文强调的时点完整性纪律。

## 22.4 领域专用嵌入

检索阶段系于嵌入模型——把文本转换为稠密向量表示的神经网络，语义相似对应几何接近。查询“利率敏感性”应当映射到接近讨论“久期风险”或“收益率曲线暴露”的段落的向量，即使那些原词并未出现。但这种理解是从训练数据学来的，在金融领域，这造成了一个鸿沟。

通用嵌入模型如 OpenAI 的 `text-embedding-3-small`（截至 2026 年初）或开源 sentence-transformer 替代品（Reimers and Gurevych, 2019），在宽泛的检索任务上表现良好，却并不熟悉金融的专业词汇、缩略语与语义关系。“alpha”在投资组合语境下与日常语言中含义完全不同。“AAPL”或“NVDA”这类股票代码的表示可能微弱或带噪。细微的概念——“forward P/E”（预期市盈率）、“covenant compliance”（契约条款合规）、“buyback yield”（回购收益率）——难以被主要在 Wikipedia 和 Reddit 上训练的模型准确捕捉。

问题比词汇更深。“美联储加息 75 个基点”这句话，与“房贷承受能力压力”和“债券组合的久期损失”在语义上相关联——但前提是模型从金融数据中学到过这些因果链条。

### FinMTEB 基准

**金融大规模文本嵌入基准**（**FinMTEB**）为这一鸿沟提供了定量证据（Tang and Yang, 2025）。FinMTEB 仿照已成为嵌入评估标准的大规模文本嵌入基准（**MTEB**），从多个维度评估模型：SEC 申报文件与业绩电话会议的检索、金融句对的语义相似度、情感检测等下游分类任务，以及按主题或行业的文档聚类。

基准揭示了一致的差距：在涉及金融行话、跨文档推理或时间指涉的检索任务上，通用模型明显落后于领域适配模型。差距在涉及定量概念（“比较毛利率趋势”）或监管细节（如描述 SFAS 157——关于公允价值计量的财务会计准则公告——的披露要求）的查询上尤为突出。

### 领域适配的嵌入模型

对生产级金融 RAG，嵌入模型应当基于金融专用评估来选择，而不能只看通用排行榜。FinMTEB 表明领域适配模型可以在金融文本上胜过通用嵌入，但排名在不同任务间并不稳定：申报文件检索、金融新闻分类、语义相似度、重排与摘要可能各自偏好不同的模型。

当前（2026 年年中）的候选名单同时涵盖托管 API 与开源/自托管模型：

- 商业选项中，Voyage 仍是金融检索的领先候选：voyage-finance-2 仍定位为金融专用模型，更新的 Voyage 4 系列则适用于高质量通用检索。值得纳入基准测试的其他托管选项包括 Gemini Embedding、Cohere Embed 4 与 OpenAI text-embedding-3-large，尤其当企业级可靠性、延迟、部署管控或多模态文档处理很重要时。
- 开源或可本地部署的模型中，Fin-E5 仍是 FinMTEB 论文中的金融适配参考模型；Qwen3-Embedding、Qwen3 重排器、BGE-M3、BGE-en-ICL 以及 E5/Mistral 衍生模型，则是当前依硬件、许可、语言覆盖与延迟约束而定的实用候选。

把任何公开排名都当作候选名单。嵌入与重排的格局变化很快，排行榜均值可能掩盖对你想构建的金融 RAG 系统最重要的那个任务。生产使用时，先在本地代表性语料——申报文件、业绩电话会议记录、研究笔记、新闻，以及应用实际要服务的查询类型——上对若干候选做基准测试，然后在确定模型之前评估检索召回率、引用精确率、延迟、向量维度、成本与重建索引负担。

### 嵌入维度与量化

一个常被忽视的实际考量是：嵌入维度直接影响存储、内存与延迟。高维嵌入（1536 或 3072 维）捕捉更多细节，但也按比例消耗更多向量数据库资源。对大型语料——数千份申报文件产生的数百万个块——这一选择举足轻重。

现代实践日益采用 **Matryoshka 嵌入**（“套娃”嵌入，Kusupati et al., 2022）：训练目标显式地把有用信息打包进每个向量的前若干维，因此截断到前 256（或 512、1024）维仍能得到可用的表示。对常规训练的嵌入做朴素截断不会有这种性质；这一性质必须经过训练才能获得。一旦具备，从业者无需重训就能提供更短的向量，以满足延迟与存储预算。类似地，**二值量化**把 32 位浮点向量压缩为 1 位表示——内存占用降低 32 倍——但精度权衡取决于语料与查询分布，应当实证验证。

### 在目标语料上评估嵌入模型

FinMTEB 这类公开排行榜能生成候选名单，但不能保证在特定申报语料、查询组合或延迟预算上的排名次序。“公开基准最佳”只是假设，不是部署结论。用以下清单在目标语料上实证评估：

1. **采样 50–100 个代表性查询**，即 RAG 系统在生产中将面对的那些。
2. **为每个查询应取回的 top-10 段落创建真实相关性标注**。
3. **用 Recall@k、平均倒数排名（MRR）与延迟比较候选模型**。
4. **按领域专用与通用模型在部署文档类型上的实测权衡做选择**。
5. **语料构成或查询分布发生变化后重新评估**。

相对于收益，这一评估的增量成本很有限。错过最相关段落的检索系统会把错误传播到下游生成。再多的提示词工程也补偿不了糟糕的检索。有了强嵌入，下一个问题是如何搜索它们——以及为什么单一检索方法几乎总是不够。**实现**：`02_domain_embeddings_comparison.py` 在一个 191 段落的 10-K 语料上，以横跨风险、技术与通用问题的 15 个查询负载运行上述协议。`BAAI/bge-large-en-v1.5`（1024 维）在平均倒数排名上以 0.675 对 0.592 领先 `all-MiniLM-L6-v2`（384 维）14.0%，在 Precision@3 上以 44.4 对 40.0 领先 11.1%。按查询类型拆解则暴露出更重要的不对称：bge-large 在技术类查询上领先（MRR 0.90 对 0.73），在风险类查询上也领先（0.61 对 0.48），而 MiniLM 仅在一般商业类问题上反超（0.56 对 0.51）。

两个模型之间 14% 的总体 MRR 差距，与单个模型内部跨查询类型的方差相当——这正是为什么“公开基准最佳”只是假设，必须在你自己的语料与查询组合上验证。

## 22.5 混合检索与向量数据库

即便有领域专用嵌入，纯语义检索仍有盲区。向量相似度擅长寻找概念相关的段落——例如“盈利能力担忧”能召回“利润率压缩”或“成本超支”。但它不擅长精确匹配：具体的股票代码、监管条款编号或引用的数字。查询“TSLA 的 Form 4 申报”，可能召回泛泛讨论内部人交易的段落，却漏掉含有特斯拉代码的文档。金融分析师经常按具体公司、日期与术语搜索，这种失效模式格外刺眼。

**混合检索**结合两种互补的检索范式（Weller et al., 2025）：

- **语义（向量）检索**：找到与查询*概念*上相似的段落，即使用词不同。擅长处理同义词与意图。
- **关键词（词法）检索**：找到包含查询中*精确词项*的段落。经典算法是 **BM25**（Best Match 25），它是词频-逆文档频率（TF-IDF）打分的精炼变体，几十年来一直是信息检索的主力（Robertson and Zaragoza, 2009）。BM25 擅长匹配股票代码、实体名称与监管编号。

并行运行两路检索并融合结果，混合检索兼顾概念相关与关键词精确。询问“AAPL 的资本回报计划”的分析师，既受益于语义检索把“资本回报”关联到“回购与分红”，也受益于 BM25 确保包含“AAPL”的段落得到应有的加权。

### 倒数排名融合

融合步骤通常使用**倒数排名融合**（**RRF**）（Cormack, Clarke, and Buettcher, 2009）。在*两个*方法中都排名靠前的文档，比只在其中一个中靠前的文档更可能相关。RRF 按文档在每个列表中排名的倒数赋分，再跨方法求和：RRF(d) = ∑_{r∈R} 1/(k + rank_r(d))，其中 R 是排序方法的集合，rank_r(d) 是文档在方法 r 中的排名，k 是平滑常数（通常取 60）。未出现在某个排名列表中的文档在该列表上贡献为零。

举个例子，假设对查询“AAPL supply chain”检索到三份文档，排名如下：

| 文档 | BM25 排名 | 语义检索排名 |
| --- | --- | --- |
| A（精确匹配股票代码） | 1 | 15 |
| B（供应链讨论） | 10 | 2 |
| C（泛泛提及 AAPL） | 50 | 8 |

*表 22.1：排名融合示例*

取 k = 60，RRF 得分为：

- RRF(A) = 1/61 + 1/75 ≈ 0.0297
- RRF(B) = 1/70 + 1/62 ≈ 0.0304
- RRF(C) = 1/110 + 1/68 ≈ 0.0238

文档 B 排第一。它在两个列表中都稳定靠前，胜过 A 的 BM25 第一名——后者被薄弱的语义排名拖了后腿。这正是 RRF 的典型偏好：相比在单一信号上称霸、在另一信号上掉队的文档，它更青睐被*多个*信号同时排在前面的文档。

RRF 简单而稳健，无需训练，并能自动适应不同的查询类型。学习型融合——训练一个模型来最优加权各检索分数——通常只带来边际改进，却增加复杂度。在一个 200 段落的 10-K 语料上、以混合实体密集型与概念型查询的 15 个查询负载测试，`03_hybrid_retrieval.py` 测得混合检索（RRF）的 MRR 为 0.443，BM25 为 0.349，领先 27%，且这一优势在精确率与召回率上同样成立。相比之下，一个在通用网络语料上训练的交叉编码器重排阶段，使 MRR 相对纯混合检索下降 36%——一个有用的警示：现成的重排器在金融段落上可能失准。*图 22.3* 展示了并行的向量检索与关键词检索如何经 RRF 合并。

### 超越双编码器：检索架构光谱

生产中的稠密检索通常使用**双编码器**（bi-encoder）——把查询与每个文档独立地各嵌入为一个向量，相似度打分因此归结为对预计算向量的快速点积。双编码器高效，但丢失了细粒度的 token 级对齐；**交叉编码器**（cross-encoder，见 *22.6 节*）能找回这一信号，但代价高得多。

两个极端之间是**后期交互检索**（late-interaction），以 **ColBERT**（Contextualized Late Interaction over BERT，基于 BERT 的上下文化后期交互）及其后继者为代表。这类模型为每个文档存储逐 token 嵌入，查询时把相似度计算为各查询 token 对文档 token 的最大值之和（“MaxSim”操作）。后期交互模型能捕捉单向量双编码器错失的 token 级匹配，而成本只有交叉编码器的零头，因此适合大型语料的第一阶段检索。代价是索引体积：存储逐 token 向量所需的存储远多于单向量方案。

对多数金融 RAG 部署而言，双编码器检索加交叉编码器重排（*22.6 节*）仍是务实之选；当单向量嵌入经调优后仍持续漏掉相关段落时，值得评估后期交互。

### 查询增强技术

原始用户查询往往不利于检索。分析师可能问：“他们中国的业务怎么了？”检索系统必须把“他们”解析为具体公司，把“中国业务”匹配到“亚太分部”或“中华人民共和国（PRC）营收”，并处理模糊的时间表述。若干技术可以应对：

- **查询扩展**：自动添加同义词或相关词。“中国业务”扩展为“PRC”、“亚太”、“大中华区”。领域专用的扩展词典（把“回购”映射到“share repurchase”与“capital return”）尤其有价值。
- **假设性文档嵌入（HyDE）**：不直接嵌入查询，而是先用 LLM 生成一个假设性答案，再嵌入该答案（Gao et al. 2023）。“该公司中国业务因监管逆风下滑 15%”这一假设，可能比稀疏的原始查询召回更多相关段落。HyDE 增加延迟（检索前多一次 LLM 调用），也引入风险：如果假设性答案是错的，检索就会偏向错误的段落。应在复杂、对话式、稀疏关键词匹配明显不足的查询上选择性使用 HyDE，并实证验证检索质量。
- **查询分解**：对多跳问题，把查询拆成子问题。“比较苹果与微软的研发支出趋势”被拆成两个独立的检索查询，结果在生成前合并。这避免了要求检索系统找到同时讨论两家公司的段落——这样的段落可能并不存在，即使信息分别可在不同章节中获得。

### 向量数据库选型

索引后的嵌入与元数据必须存放在为相似度搜索优化的系统中。实践中，团队在托管服务、自托管向量数据库、轻量本地选项与 `pgvector` 等数据库扩展之间选择。产品名称的更迭慢于功能特性的变化，因此持久的选型标准比任何特定时点的对比表更重要。对金融 RAG，先问三个问题：系统是否支持在**近似最近邻**（ANN）搜索之前做元数据过滤？能否干净地接入混合检索技术栈？是否契合组织现有的运维体系？

对生产级金融 RAG，原生支持混合检索的数据库（Weaviate、Pinecone、Milvus、Qdrant）能简化架构。原型阶段，ChromaDB 加独立 BM25 索引是经济的选择。已深度使用 PostgreSQL 的组织可以用 pgvector 避免新增基础设施；同样，运行 OpenSearch 或 Elasticsearch 的企业可以利用其原生混合检索与一流的 RRF 支持，而不必引入独立的向量数据库。

### 过滤检索

金融查询常常带有隐式或显式的过滤条件：“苹果 2023 年的 10-K”、“最新申报中的风险因素”。与其只依赖相似度，不如按元数据做**预过滤**以提高精确率。

现代向量数据库原生支持过滤搜索：*在*计算相似度得分*之前*施加元数据约束（`company = "AAPL"`、`fiscal_year = 2023`、`document_type = "10-K"`）。实现方式很重要：预过滤（在 ANN 搜索之前施加元数据约束）能保住召回率，因为搜索只在相关子集上进行。

**后过滤**（先搜索完整索引，再丢弃不匹配的结果）在相关子集相对语料很小时会严重损失召回。多数生产级向量数据库现已原生支持预过滤。至少应为每个块打上：公司标识、财年、财季、文档类型（10-K、10-Q、业绩电话会议）、申报日期、章节标题与页码。这套元数据模式覆盖最常见的金融过滤条件，并支撑 *22.6 节* 讨论的引用格式。

一个具体例子可以说明风险：分析师问“管理层对 2024 年给出了什么指引？”而未加财年约束，可能召回恰好提到 2024 年的 2022 年前瞻性陈述——看似合理、引用规范，却危险地过时。

检索是 RAG 质量的地基。再多的提示词工程也补偿不了检索阶段没有找到的段落。但检索返回的是一组排序后的候选，而非经过验证的答案。下一节处理最后两个阶段——重排候选集以提升精确率，并约束 LLM 的生成只产出有据可引的回答。

## 22.6 重排与基于约束的提示词

检索以召回为目标——广撒网以确保相关文档被捕获。初始检索可能返回 20–50 个候选块，有些高度相关，有些是噪声。两项技术弥合这一差距：重排以锐化精确率，基于约束的提示词以强制锚定。

### 交叉编码器重排

**重排**步骤充当检索与生成之间的精修过滤器。初始检索使用快速但近似的手段（如向量相似度或 BM25），重排则用更强大的模型对每个候选重新打分，以判定精确相关性。

典型架构使用**交叉编码器**——把查询-文档对作为单一输入、输出相关性得分的模型（Nogueira and Cho, 2020）。与双编码器（独立嵌入查询与文档）不同，交叉编码器关注细粒度的 token 级交互，相关性判断更准确，代价是逐对计算：

1. **初始检索**：快速搜索返回前 50 个候选块。
2. **重排**：交叉编码器对每个块相对查询打分。
3. **选择**：得分最高的 top-5 块交给 LLM。

对 50 个块重排的延迟通常为 100–200 毫秒——对分析类应用可以接受，但对实时场景可能过高。可选方案包括 Cohere 的 Rerank API、Sentence-Transformers 库的开源交叉编码器，以及在金融问答数据集上微调的领域专用重排器。

### 上下文窗口管理

现代 LLM 提供 128K 到 100 万以上 token 的上下文窗口，诱人的问题随之而来：为什么不直接传入整份 10-K，让模型自己找需要的部分？

这种“长上下文”路线有三个显著缺陷。第一，LLM 难以关注超长上下文中段的信息——Liu et al. (2024) 记录了强烈的首因与近因效应，而非对整个窗口的均匀利用。第二，推理成本随输入 token 数增长：在 5K token 就够用的情况下传入 200K token，成本大增而准确性未必提升。第三，产出首个 token 的等待时间显著拉长。“迷失在中间”（lost in the middle）效应因模型与版本而异；更新的架构可能部分缓解它。在假设特定失效形态之前，先在目标模型上做基准测试。

务实的建议：把长上下文窗口作为复杂多跳查询的后备手段，但保持精准检索为默认。由精准相关块组成的 5–10K token 上下文，通常优于由松散相关材料组成的 100K+ token 上下文。

### 基于约束的提示词

对抗幻觉的最后一道防线是生成提示词本身。生产级 RAG 提示词施加显式约束，以强制锚定与可验证性：

- **角色设定**：“你是一名对 SEC 申报文件开展尽职调查的资深金融分析师。”
- **上下文约束**：“仅基于所提供的上下文回答。不要使用外部知识。”
- **不确定性处理**：“如果上下文缺乏足够信息，请明确说明该信息不可得。”
- **引用指令**：“对每一条事实性断言，以 [第 X 页，第 Y 节] 的格式附上内联引用。”
- **结构化输出**：“按以下结构组织回答：(1) 直接答案，(2) 带引用的支撑证据，(3) 注意事项或局限。”

一个关键警示：**引用并不自动忠实**。LLM 可能引用并不支撑断言的段落、跨块混合信息，或生成不存在但看似合理的页码。生产系统应当校验引用保真度——例如要求模型在每条引用旁摘录一个支撑性短语，或实现自动断言-证据对齐，把每条引用对照检索到的上下文加以验证。一个轻量校验步骤：按页码/章节引用取出每段被引文本，计算断言与被引文本之间的语义相似度，将低于阈值的配对标记出来供人工复核。这一步能抓住最常见的失效——看似合理却无支撑的引用——而不需要第二次 LLM 调用。*22.7 节* 讲述如何系统性地度量引用保真度。

配套 notebook `05_10k_rag_assistant.py` 演示了本章使用的更窄但更贴近生产的模式：引用受限的回答、上下文不足时的显式弃答，以及对检索覆盖与引用存在性的轻量检查。

### 数值可靠性与工具验证的计算

金融查询经常要求的不只是文本检索，还有算术：“营业利润率的同比变化是多少？”“流动比率与行业中位数相比如何？”LLM 能取回正确的证据，却经常算错——这一失效模式不同于幻觉：源段落正确，派生答案却错了。

数值问题的可靠模式是一个四阶段流水线：

1. 检索证据，包括表格切片。
2. 把数字提取到结构化模式中（单元格、单位、期间、分部）。
3. 通过代码或工具计算，而非让 LLM 来算。
4. 生成带引用与可复现计算轨迹的叙述性解释。

这一“检索-提取-计算-叙述”模式把算术交给确定性工具，把 LLM 约束在它擅长的事情上：综合与解释。智能体框架（*22.9 节*）把这一点形式化为让 LLM 把代码解释器作为显式工具调用。即使没有完整的智能体架构，要求结构化数值输出（含提取值与计算结果的 JSON）并以程序化方式验证算术，也能抓住大部分常见的量化错误。

### 程序化输出校验

提示词层面的约束对生产金融系统是必要的，但并不充分。程序化校验加上第二层保障：结构化输出解析（JSON 模式、函数调用）确保 LLM 的响应符合模式；断言级验证流水线把每条断言对照检索上下文核查；护栏框架（如 NeMo Guardrails、Guardrails AI）通过代码而非仅靠提示词指令来强制输出约束——主题遵从、毒性过滤、格式合规。提示词约束与程序化校验的组合在生产部署中日益常见。

### 作为契约的提示词

这套基于约束的方法把 LLM 从生成式神谕转变为综合引擎。模型的任务不再是“知道”答案，而是阐明所给证据支撑什么。与解析得当、元数据齐全、检索精准的上下文相结合，这种架构产出的回答*以可验证为目标*——分析师可以沿着引用把断言追溯到来源并独立确认。“以可验证为目标”与“自动已验证”之间的差距，正是生产工程投入的焦点。

提示词是系统与 LLM 之间的契约。含糊的提示词招致幻觉；精确而具约束力的提示词强制锚定。完整的 RAG 技术栈就绪之后，下一个挑战是像对待任何 ML 系统一样对待它：定义指标、构建评估集、在数据上迭代。

## 22.7 诊断 RAG 流水线瓶颈

没有系统性评估，RAG 系统就是一个难以调试的黑箱流水线。它可能检索到无关文档，漏掉关键信息，或者在上下文明明正确时仍然幻觉。在少数测试查询上的偶然成功会制造虚假信心。诊断流水线*在哪一环*失效——检索、上下文、综合、计算还是弃答——决定了*该修什么*。

### 失效模式

RAG 失效可分为几类，各自需要不同的修复手段：

- **检索失效**（上下文召回率低）：正确信息存在于知识库中，但检索阶段没能取回。回答错误，人工检索语料能发现未被取回的相关段落。

*修复*：改进嵌入、调整混合检索权重或优化分块。

- **上下文失效**（上下文精确率低）：检索找到了部分相关文档，但混入过多噪声，稀释了信号。检索到的上下文包含沾边的材料，却遗漏关键细节。

*修复*：调整重排器阈值、改进元数据过滤或调整分块粒度。

- **综合失效**（忠实度低）：检索成功、上下文准确，但 LLM 生成了错误或幻觉的回答——误读上下文、未能综合，或无视锚定约束。

*修复*：打磨提示词、换用能力更强的 LLM，或实现答案验证。

- **计算失效**（证据正确、算术错误）：综合失效在定量查询上的变种。系统取回了正确的表格或段落，但 LLM 把派生值算错——报出错误的同比变化或用错公式。这一失效对标准忠实度指标不可见，因为被引证据是对的，错的只是计算。

*修复*：把算术交给代码（*22.6 节*），并以程序化方式验证数值输出。

- **弃答失效**：有些问题在已索引的文档中没有答案——用户问的是知识库中不存在的公司、未覆盖的时间段，或根本没有披露过的信息。校准良好的系统应当弃答而非编造。把拒答质量与其他指标一起评估：系统能否正确识别自己信息不足？能否恰当地传达不确定性？

### RAGA 指标与断言级评估

**检索增强生成评估**（**RAGA**）为每类失效模式提供自动化指标（Es et al., 2024）。FinDER（Choi et al., 2025）等数据集为金融 RAG 评估提供了专门设计的标准问答对：

| 指标 | 衡量内容 | 失效模式 |
| --- | --- | --- |
| 上下文精确率 | 检索到的块与查询相关吗？ | 上下文失效 |
| 上下文召回率 | 检索是否返回了全部必要信息？ | 检索失效 |
| 忠实度 | 回答是否锚定于上下文（无幻觉）？ | 综合失效 |
| 答案相关性 | 回答是否回应了用户的问题？ | 综合失效 |
| 弃答质量 | 证据不足时系统是否拒答？ | 无法回答的查询 |

*表 22.2：RAGA 指标*

这些指标通常让 LLM（往往是 GPT-4）充当裁判，对照标准标注或通过自动推理来评估检索上下文与生成回答的质量。虽然不完美，但它们为流水线性能的基准化和持续改进提供了一条可扩展的路径。

RAGA 度量答案层面的质量，但高风险金融应用需要更细粒度的诊断。**RAGChecker**（Ru et al. 2024）把生成的答案分解为原子断言，逐条核对断言与检索证据之间的蕴含关系，得出**无依据断言率**——不被任何检索段落支撑的断言占比。这与 RAGA 形成互补：一个回答可能在整体忠实度上得分很高，却包含一条最要命的无依据数值断言。生产部署应把无依据断言率与 RAGA 指标一起跟踪，并在人工标注子集上校准 LLM-as-judge 分数以防虚假信心。`04_ragas_evaluation.py` 在一个小型测试集上实例化这一四轴评估框架，展示了失效模式分离的实际效果：检索得分 0.33（最薄弱环节），有据回答质量 0.65，弃答 F1 0.50，安全鲁棒性 0.67；无依据断言率为 0.50，而不安全动作率为 0.17——这提醒我们，无依据的文本生成通常是更高频的失效，也是护栏投入的优先方向。

诊断工作流有五步：

1. **构建评估集**：50–100 个带标准答案与源段落的代表性查询。按难度（单跳事实、多跳推理、比较）与文档类型分层。纳入 10–20% 无法回答的查询。由领域专家验证标准答案——自动生成的标注会引入评估框架本应检测出的同类偏差。
2. **计算基线指标**：在评估集上运行 RAGA，确立上下文召回率、上下文精确率与忠实度。
3. **隔离失效模式**：上下文召回率低 → 检索问题。上下文精确率低 → 排序问题。忠实度低 → 综合问题。
4. **施加针对性修复**：改进最薄弱的组件——优化嵌入、调重排器或打磨提示词——而不是漫无目标地改动。
5. **持续监控**：使用 TruLens 等可观测性工具跟踪生产中的 RAG 性能，及时发现退化（例如由语料漂移或新查询模式所致）。

这种诊断能力把 RAG 从黑箱流水线变成可以系统性调试和改进的工程系统。没有度量，调优就是猜谜；有了度量，任何改动都能对照可观测的权衡来评估。金融工作流给上述流程追加一条要求：**引用可追溯性**——把每一条事实性断言绑定到具体源段落的能力。每个评估周期都把它与 RAGA 指标一起打分。

### 把评估框架扩展到对抗性输入

迄今讨论的失效模式都假设输入是良性的。当语料本身含有恶意指令（例如经投毒文档注入的提示词），或用户构造旨在绕过锚定约束的对抗性查询时，一种性质不同的威胁就出现了。如果系统具备工具调用能力（*22.9 节*），攻击面还会进一步扩大。安全应与准确率放进同一个评估框架，而不是独立的审计：在对抗性提示下复用诊断指标——无依据断言率、引用失败率与弃答行为——让鲁棒性的退化与准确率的退化以同样的方式显形。notebook `08_rag_security.py` 实现了一套覆盖提示词注入、检索污染与动作注入场景的压力测试。在一个含四个攻击样本的测试集上，简单防御（输入清洗加检索感知拒答）把不安全动作率从 0.50 压到 0.00，把无依据断言率从 1.00 降到 0.25（相对下降 75%）——这说明可观的鲁棒性提升并不需要更换模型，而残余的 0.25 无依据断言率则诊断出防御栈仍然漏掉的部分。

### 迭代纠错回路

上述工作流假设由人来审阅指标并决定修什么。一种新兴模式把这个回路自动闭合：**纠错式 RAG**（**CRAG**）与 **self-RAG** 架构让 LLM 自身评估检索质量，并在初始结果不足时重新查询。若检索到的上下文得分低于置信阈值，系统会改写查询、扩大搜索范围或调用其他检索策略，然后再生成回答。这把静态的“先检索后生成”流水线变成迭代回路——通往 *22.9 节* 智能体框架的自然桥梁。代价是延迟：每轮纠错多一次 LLM 调用。交互式应用应限制纠错轮数；批量分析任务通常可以接受额外延迟。

评估框架就绪后，下一节转向部署：把完整的 RAG 技术栈应用于真实金融工作流，并针对不同用例在 RAG 与微调之间做出战略选择。

## 22.8 应用与战略选择

本节把 *22.2–22.7 节* 的 RAG 架构应用于三个金融用例，然后与微调做战略比较。

### 10-K 尽职调查助手

金融 RAG 的首要用例，是面向冗长致密的监管申报文件的尽职调查助手。一家大型公司的 SEC 10-K 年报可达 200–300 页，涵盖财务报表、管理层讨论、风险因素、法律诉讼与分部分析（Lopez-Lira, 2023）。人工检索特定信息——跨年度比较营收驱动因素、把风险披露与业绩对应起来、提取定量承诺——动辄数小时。

设计良好的 RAG 系统改变了这一过程。分析师提出复杂的多跳问题，并获得带页码引用的综合回答。

**示例查询**：

`基于 MD&A 与风险因素章节，营收增长 10% 的主要驱动因素是什么？文中引用了哪些可能威胁这一增长的风险？`

这个问题迫使系统连接文件的两个不同区域：MD&A 中关于增长驱动的讨论，与风险因素中关于增长可能被什么侵蚀的讨论。朴素流水线在此捉襟见肘：碎片化的块模糊了跨章节关系，宽松的检索可能只打捞出故事的一面。生产中的解药正是本章前文构建的完整技术栈：结构感知摄取、精准检索与引用受限生成。其核心特征是**可验证性**：生成回答中的每一条事实性断言，都应指向分析师可以直接查验的页面或章节。**实现**：见 `05_10k_rag_assistant.py`，一个紧凑的章节级助手，演示本地申报摄取、top-*k* 检索、引用受限提示词与轻量检索/引用诊断。notebook 将 LlamaParse 与更丰富的检索后端标注为生产升级项，而非已实现功能。配套的 `01_sec_filing_pipeline.py` 覆盖 EDGAR 访问，以及时点过滤与引用追溯所需的元数据。

生产部署还需要技术流水线之外的治理控制：访问控制、对提示词与检索上下文的审计日志、留存策略，以及对外共享输出的人工复核（*第26章*）。安全考量——提示词注入、检索污染、引用滥用——用 *22.7 节* 的诊断框架评估；`08_rag_security.py` 实现了专用的压力测试框架。

### 对比案例研究：ESG 分析

ESG 分析恰好展示了 *第10章* 的分类范式与 RAG 推理范式的对照。

先回顾**微调分类**路线（如 *第10章* 所示）：在标注 ESG 文本上微调的判别式 Transformer（Baltussen et al. 2025; Zhao, Li, and Zheng, 2020），把新闻文章或披露片段归入预定义的分类，如“环境-风险”（Environmental-Risk）、“社会-机遇”（Social-Opportunity）或“治理问题”（Governance Concern）。

工作流：收集标注数据集，微调带分类头的 Transformer，对流入的文档运行，输出类别标签与置信度分数。这一路线可规模化，因为它把开放式文本变成紧凑信号，可输入筛选、因子构建与组合约束。局限是结构性的：模型只能在固定分类体系内工作，无法解释*为什么*把一篇文档归入某类，也无法回答后续追问。输出是一个分数，不是证据链。

**基于 RAG 的尽职调查**则在一家公司全文版可持续发展报告之上构建 RAG 系统——那些 100 多页、详述碳排放、供应链实践、多元性指标与治理架构的文件。工作流：以结构感知分块解析并索引可持续发展报告，用领域专用嵌入构建 RAG 查询引擎，让分析师用自然语言提出开放式问题，输出带具体页码与章节引用的叙述性回答。

**示例查询**：

`总结公司的范围 2（Scope 2）减排战略，列出其关键绩效指标（KPI），并指出公开承诺的五年目标——附页码引用。` 这一路线支持深度定性分析：分析师可以探究细节、继续追问，并获得可验证的带引用回答。它增强人类分析师的判断，而不是用一个分数取代判断。其局限是运营性而非概念性的：它需要持续维护的文档语料、检索基础设施，以及围绕引用、弃答与治理的更强管控，而且不会天然产出系统化策略所需的可规模化数值时间序列。权衡见下表：

| 维度 | 微调分类器 | 基于 RAG 的问答 |
| --- | --- | --- |
| 主要输出 | 数值分数、标签 | 带引用的叙述性回答 |
| 可扩展性 | 高（批量处理） | 中（逐查询） |
| 灵活性 | 低（固定分类体系） | 高（开放式问题） |
| 可验证性 | 间接（模型置信度） | 直接（来源引用） |
| 知识更新 | 需要重新训练 | 更新语料，无需重训 |
| 最佳用例 | 系统化因子构建 | 基本面尽职调查 |

**实现**：见 `06_esg_rag_vs_finetune.py`，一个风格化的并排对比。该 notebook 旨在澄清“产出标签的分类器”与“带引用叙述的工作流”之间的架构权衡，并非生产延迟基准。

### 生成模型选型

战略选择不止于 RAG 与微调之辨，还延伸到生成模型本身。**商业 API**（如 GPT、Claude、Gemini）能力最强，但要求把文档发送到外部服务器——对许多有严格数据驻留要求的金融机构而言，这直接排除了这一选项。开放权重模型（如 Llama 3、Mistral、DeepSeek、Qwen）可在本地或私有云环境中运行，以复杂任务上较低的能力为代价保住数据主权。

差距正在缩小：在上下文已提供大部分所需信息的、约束良好的 RAG 任务上，**开放权重模型**日益接近商业 API 的质量。按四条标准选择：能力（模型能否可靠遵守锚定约束？）、成本（预期用量下的单次查询经济性）、延迟（对该用例是否可接受？）与数据驻留（专有文档能否离开自家基础设施？）。

许多生产部署采用分层方案：高频常规查询用开放权重模型，需要更强综合的复杂分析任务用商业 API。

### 生产生命周期

演示跑通之后，团队大部分时间都花在流水线架构没有覆盖的运维问题上：

- **增量索引**：检测新申报、重述与修订；只对变更的片段更新嵌入，而不是重建整个语料的索引。
- **语料版本管理与可复现性**：把语料快照、嵌入模型、重排器、提示词模板与生成模型作为整体做版本管理。为每次响应存储一个紧凑的“检索包”（retrieval bundle）（查询、检索到的块、证据片段、模型版本、回答），以支持审计与复现。
- **删除与留存**：实现墓碑机制（tombstoning）、法律保全与带审计日志的留存规则——这是受监管环境中数据不能一删了之的硬性要求。
- **缓存**：缓存查询嵌入、重排器结果与高频问答，并把过期策略与申报更新周期挂钩。

这些问题是生产部署的前置条件，不是事后补丁。

### 受监管环境中的部署

金融 RAG 系统运行在通用 AI 部署不会遇到的监管预期之下。经纪自营商监管者与欧盟《人工智能法案》（EU AI Act）如今都把生成式 AI 纳入文档记录、监督与透明度义务的范围；随着监管者摸索如何区分传统模型与生成式、智能体式系统，大型银行的模型风险监管也在独立演进。

具体规则因司法辖区与机构类型而异，但设计层面的启示是稳定的：从一开始就为可审计性与溯源而构建——访问日志、带版本的检索包、留存与墓碑机制——因为把这套控制事后加装到运行中的系统上，远比一开始就设计进去昂贵得多。治理与 MLOps 的完整论述见 *第26章*；这里的原则是：让合规与模型风险团队尽早参与，而不是部署之后。

### 结构化数据提取：机构持仓

RAG 技术自然地延伸到自由文本问答之外——从监管申报文件中提取结构化数据。SEC 13F 申报——机构股票持仓的季度披露——为量化策略提供了丰富的信号来源。以程序化方式解析这些文件并构建共同持股图，可以揭示拥挤模式、机构动量以及补充传统价量信号的网络特征。共同持股特征捕捉到价量数据无法反映的慢变机构持仓：当多家大型基金集中持有相同股票时，由此产生的拥挤风险会造成标准动量或价值因子察觉不到的同步平仓脆弱性。机构与股票的二部图也为 *第23章* 的图神经网络方法提供了天然输入——在持仓网络上做消息传递，可以把机构行为的信息传播到相互关联的证券。

本节讨论的每个应用都把 RAG 流水线视为静态的“先检索后生成”序列。下一节引入智能体框架：LLM 可以自行决定*何时*检索、调用*哪些*工具，以及*如何*分解多步研究问题——把 RAG 从固定流水线变成自主推理回路中的一个组件。

**实现**：`07_institutional_holdings_graph.py` 展示了一条通过 EDGAR 获取 13F 申报、构建共同持股网络并工程化横截面特征的流水线。

## 22.9 智能体框架初探

本章的 RAG 系统是被动的：等待问题、检索上下文、生成回答。下一步的演进是从问答走向**自主行动**——能够规划、使用工具并达成目标的 AI 智能体。

**AI 智能体**是 LLM 充当自主过程控制器的系统，该过程可以规划、使用工具并采取行动。核心组件包括：

- **LLM 控制器**：解读目标、规划步骤并决定行动的推理引擎
- **工具**：智能体可调用的外部能力——用于文档检索的 RAG 系统、网页搜索 API、用于数值计算与统计分析的代码解释器、数据库查询接口，或提供实时行情与基本面数据的金融 API
- **记忆**：跨交互持久化的上下文，使智能体得以维持状态、从过往行动中学习并在会话中积累知识

这一架构支持远超静态 RAG 流水线的多步问题求解。智能体不只是回答单个问题，还能把复杂目标分解为子目标，串行或并行执行，处理失败，并综合结果。

### ReAct 范式

LLM 智能体的基础框架是 **ReAct**（源自 *Reason* 与 *Act*）（Yao et al., 2023），它把行为组织为一个迭代循环：

1. **思考（Thought）**：智能体推理自己已知什么、下一步需要做什么。
2. **行动（Action）**：基于这一推理，智能体调用工具或采取行动。
3. **观察（Observation）**：智能体观察行动的结果。
4. **重复（Repeat）**：循环继续，直到智能体判断目标已达成或需要向用户澄清。

这一推理、工具调用与观察的循环，成为 *第24章* 更完整的智能体架构的起点。

该模式可扩展到复杂的分析工作流：把研究问题分解为子查询，为每个子查询调用合适的工具（文档检索、API 调用、计算），观察结果，迭代直至形成完整的回答。

### RAG 作为智能体工具

成熟的智能体并不取代 RAG，而是把 RAG 当作众多工具中的一个来*使用*。本章构建的 RAG 系统——解析过的知识库、混合检索、生成引用的提示词——成为智能体工具箱中“文档分析”工具的一部分，与网页搜索、代码解释器、数据库查询和金融 API 并列。

智能体的 LLM 控制器编排这些工具，依据用户目标与先前行动的结果决定调用哪个。多工具编排的价值在问题无法仅凭文档回答时显现：“公司 X 当前的 EV/EBITDA（企业价值/息税折旧摊销前利润）相对其五年均值如何？”需要文档检索提供定性背景、数据库查询提供历史基本面、再做一次计算得出比率与比较。没有任何单一 RAG 流水线能包办三者；智能体把每个子任务路由给合适的工具。

并非所有问题都需要智能体——对结构化、可预测的任务，设计良好的 LLM 工作流往往胜过智能体；智能体架构应留给真正开放式的探索（Bowne-Anderson, 2025）。

### 业界采用

金融机构正从试验走向早期部署，但前沿比公开宣传的更窄。内部研究助手、文档分诊工具与面向分析师的检索系统，已在越来越多的机构中小规模投入生产。

**多智能体架构**——由一个协调者调度文档、数据库与计算等专职智能体——在研究文献中已有充分描述（Saha et al., 2025; Yu et al., 2024; Kong et al., 2024），但受监管金融领域大多数已部署的智能体系统，在每个触及外部状态的动作——下单、客户沟通或账户变更——上仍保留**人在回路**（human-in-the-loop）。

**Man Group** 公开讨论过用智能体 AI 生成量化交易信号（Fang and Moore, 2025）——之所以引人注目，是因为鲜有机构公开把智能体系统接入实盘信号生成工作流，而非纯研究助手用例。轨迹是清晰的——从特征到综合再到行动——但基准演示与经过审计的生产级智能体流水线之间仍有很大距离。RAG 提供的是地基——有据的知识检索——智能体系统由此构建。*第24章* 将给出完整实现。

## 22.10 小结

检索增强生成是在金融研究中使用大语言模型的核心架构——它拒绝把模型输出当作不证自明的事实。核心设计原则很简单：模型应当在检索到的证据之上综合，而不是凭借它恰好记得的东西。但让这一原则在实践中奏效，靠的不只是一个向量库加一条提示词。金融文档要求结构感知摄取、领域敏感的嵌入、混合检索、重排、基于约束的提示词，以及对数值计算的确定性处理。最终的产物不是不透明的神谕，而是可审计的研究工具——它的每条断言都能追溯到具体来源。

一条战略边界区分了 RAG 与微调。目标是可重复的技能（如在稳定标签上做分类或提取）时，微调合适；目标是在变化的文档与问题之上做有据分析时，RAG 合适。这一区分明确之后，评估也随之明确：分别诊断检索、上下文、综合、计算与弃答中的失效，并以有据的有用性而非表面流畅来评判系统。

下一章介绍知识图谱——当问题依赖于路径、网络与时间结构，而不仅是叙述性证据时，知识图谱把实体与关系显式化。
