# 第25章：实盘交易系统

从盈利回测到实盘执行的过渡，正是大多数算法交易项目折戟之处。失败并非因为策略缺乏优势，而是因为生产系统以种种微妙的方式偏离研究环境，逐渐侵蚀收益：特征的计算略有出入、成交假设与现实不符、信号与执行之间存在时序错配。关于**回测过拟合**的研究表明，即便是实现正确的策略，转入实盘交易后也会出现显著的业绩衰减（Bailey et al., 2015）——而这还是以实盘实现与回测完全一致为前提。

解决方案是一个统一框架：**回测与实盘两种模式运行完全相同的代码**，从构造上消除技术性差异。*第16–19章*构建的策略类、仓位配置逻辑、成本参数和风险控制并非等待重写的原型——它们经由同一个 `ml4t-backtest` 库直接移植到实盘执行，改变的只有数据来源与执行去向。本章将搭建其余的生产基础设施——经纪商集成、订单管理、流水线验证与运维流程——让你有把握地部署这些策略。

完成本章后，你将能够：

- 解释为什么研究与生产之间的技术性差异是实盘交易的首要失败模式，以及统一框架如何降低这一风险。
- 设计一种双模式、事件驱动的交易架构，使确定性策略逻辑在回测、模拟盘和实盘执行中原样运行。
- 比较经纪商、交易所与托管平台三条部署路径，并依据资产覆盖、执行质量、运维负担和控制力进行评估。
- 将订单处理建模为显式的状态机，支持部分成交、取消、拒绝、对账以及幂等的崩溃恢复。
- 在整条流水线上验证技术一致性，覆盖从原始数据与特征到预测、仓位决策和订单生成的每个环节。
- 规划分阶段的实盘上线：运用预检、影子或模拟盘交易、熔断开关与对账流程，并顾及交易场所与司法辖区的约束。

*25.1 节*介绍让同一策略代码在回测与实盘两种模式下运行的统一框架。*25.2–25.3 节*集成两个经纪商 API——Interactive Brokers 提供全球多资产接入，Alpaca 面向开发者提供美股与加密货币交易；*25.4 节*评估作为替代路径的托管平台。*25.5 节*把订单生命周期建模为显式的状态机；*25.6 节*建立流水线验证方法，确保部署前的技术一致性。*25.7 节*讨论运维就绪——熔断开关、从模拟盘到实盘的分级过渡，以及约束"什么可以部署在哪里"的监管版图。

## 25.1 从研究到生产的统一框架

量化策略研发常常沿着一条省事却易出错的路径：研究在 Jupyter notebook 里基于历史数据完成，前景看好的策略随后被改写为另一种语言或框架的生产版本，有时甚至出自另一个团队之手。同一套逻辑由此产生两份并行实现——实现 bug 也就有了两处藏身之所。

问题会随时间不断累积。研究人员改进了特征工程，生产团队就得复现这一改动；生产系统遇到边界情况，修复却不会回传到研究代码。六个月后，回测显示年化收益 15%，实盘交易却只带来 3%。差异真实存在，但找出根源既困难又耗时。

### 技术性差异

技术性差异指相同的输入在回测与实盘执行中产生不同的输出。统计性衰减源于市场确实发生了变化；技术性差异则完全是自身造成的。

最常见的来源是**特征计算的差异**：研究中的移动平均基于复权收盘价，生产中却用未复权价格；或者波动率估计采用的回看窗口略有不同。这类差异往往要等到累积效应变得可观时才会被发现。

**时序假设**构成第二类差异。研究代码在收盘时计算信号，并假设次日开盘执行；生产代码接收的数据延迟不一，执行也是异步的。回测所假设的完美同步在实践中并不存在。

**数据处理的边界情况**——缺失价格、公司行为、代码变更——让问题进一步复杂化。研究代码常常忽略这些麻烦，生产系统却必须妥善处理。就连**订单转换**也会引入差异：把信号（"AAPL 目标权重 +0.05"）变成实际订单，需要取整到有效的交易手数并顾及可用流动性，不同的实现会做出不同的选择。

### 统一框架的解决方案

统一框架从构造上消除技术性差异。同一份代码——字面意义上的同一批源文件——在两种模式下运行：

- 在**回测模式**下，框架把历史数据送入策略，按可配置的假设模拟订单执行，并记录持仓与收益——就是传统回测，只是用的是生产代码。
- 在**实盘模式**下，框架连接经纪商 API，把实时数据送入完全相同的策略逻辑，并将订单路由至执行环节。没有转换层，策略本身也没有第二套实现。

在 ML4T 技术栈中，这一模式分布在两个配套库里。`ml4t-backtest` 提供第16–19章介绍的事件驱动研究与验证引擎；`ml4t-live` 通过经纪商适配器、实时数据源和安全控制，为模拟盘与实盘交易提供同一个 `Strategy` 接口。关键的连续性在策略层：决策逻辑保持不变，实盘部署只是在其外围增加了经纪商、数据源与风险管理基础设施。

### 双模式运行架构

该架构建立在四条设计原则之上：

1. **数据与执行的抽象接口**屏蔽了来源：策略通过一个不关心数据来自历史数据库还是实时 WebSocket 行情的接口获取市场数据；订单则经由统一的执行接口路由，回测时发给模拟器，生产中发给经纪商。
2. **信号生成必须是确定性的**——给定相同的市场状态，策略产生完全相同的信号。这意味着要避免依赖系统时间、各次运行不一致的随机种子，或在环境之间变化的外部状态。
3. **两种模式共享事件驱动的内核**。回测中，事件从历史数据回放；实盘交易中，事件来自市场数据源。二者由同一套事件处理器处理。
4. **持仓状态、订单状态与策略状态**在两种模式下以完全相同的方式维护。框架负责持久化与恢复，确保重启后的实盘系统能从保存的状态继续运行。

### 从模拟到实盘

*第16–19章*中模拟的策略，就是等待接入实时数据源的生产代码。在那些章节里，每个案例研究都定义了一个 `Strategy` 子类，其 `on_data()` 方法接收市场数据、计算信号，并通过框架的执行接口提交订单。`Engine` 在回测模式下用历史数据运行该策略：第16章的 ETF 动量策略沿用同一个 `MLSignalStrategy` 类，依次叠加仓位配置（*第17章*）、交易成本建模（*第18章*）和风险管理（*第19章*），逐层累积起投资组合构建逻辑、成本感知约束与自适应风险控制。

转入实盘，意味着保留同一个策略类，把历史运行时替换为 `ml4t-live` 的 `LiveEngine`、经纪商适配器和实时数据源。`on_data()` 逻辑、仓位配置规则与组合意图原封不动地保留下来；围绕这一策略，实盘技术栈补上了回测不需要的运维组件：异步经纪商连接、启动检查、影子模式、持久化的风险状态和受保护的订单提交。*第17章*的 `WeightFollowerStrategy`——它把模型生成的目标权重转换为再平衡订单——成为实盘执行策略；*第18章*的成本模型参数（价差估计、冲击系数、换手率约束）成为实盘成本预算，实际执行将以此为基准来衡量；*第19章*的熔断开关阈值与回撤阈值成为由经纪商封装层强制执行的实盘安全控制，而不再是模拟器内部的假设。这种连续性正是统一框架的回报。九个案例研究——ETF、加密货币永续合约、期货、外汇、股票与期权——各自定义了从特征到风险受控执行的完整流水线；只要 *25.6 节*介绍的流水线验证测试确认了技术一致性，任何一条流水线都可以在不重写策略逻辑的前提下从回测迁移到实盘运行时。

框架提供了策略接口，剩下的工作是把它接入具体的经纪商。接下来两节集成 Interactive Brokers 与 Alpaca——对部署本书策略的从业者（尤其在美国）而言，这是最相关的两个经纪商 API。

**实现**：`01_unified_framework_demo` 在共享的历史回放上演示信号一致性：同一个 `DualMAStrategy` 在回测与实盘式执行中产生匹配的信号，策略代码零改动——统一框架的核心论断，浓缩为一次并排对比。

`02_etfs_deployment_loop` 是本章的核心演示，在真实 ETF 数据上展示完整的再训练与部署循环：通过 `ml4t-data` 刷新 ETF 面板数据，重新训练 ETF 案例研究中确定的 Ridge 回归器，用 `ml4t.backtest.Engine` 回放实盘窗口以生成离线参考信号记录，并通过 Alpaca 股票模拟盘提交最新的 top-K 篮子——再逐个标的把实盘经纪商提交与离线记录对账。*25.7 节*会再次引用它作为部署循环的参考实现。

## 25.2 集成 Interactive Brokers

**Interactive Brokers**（**IBKR**）通过 **Trader Workstation**（TWS）应用或 IB Gateway 套接字 API、Client Portal API，以及 FIX/CTCI 等机构级接口提供全球多资产接入。IBKR Pro 的美股与 ETF 阶梯佣金约为每股 0.0035 美元起；符合条件的美国证券账户，在账户权益达到 10 万美元（监管下限）或更高（取决于经纪商风险限额）后，即可申请组合保证金。对需要广泛品种覆盖的系统化交易者来说，IBKR 仍是最灵活的面向散户的经纪商技术栈之一。

### TWS 与 IB Gateway

针对散户账户，IBKR 提供两种连接方式，各适合不同的使用场景：

- **TWS** 是完整的桌面应用，提供手动交易的图形界面以及 API 接入。TWS 运行需要物理（或虚拟）显示器，这给无头服务器部署带来麻烦；不过，它的可视化反馈在开发与调试阶段颇有价值。
- **IB Gateway** 以更少的图形开销提供同一 API 的接入，可在服务器上无头运行，资源占用低于 TWS。就生产部署而言，IB Gateway 通常是更好的选择。

两者都需要定期刷新的认证。自动化登录方案固然存在，但必须仔细考量安全问题——这些凭据拥有账户的完全访问权限。

### 连接模式

面向散户与开发者的主流工作流使用 IBKR 事件驱动的长连接套接字。`ib_async` 库提供了更高层的 Python 接口，用起来更接近常规的同步或 `asyncio` 编程，从而简化了底层的回调式套接字 API。每个连接由一个客户端 ID 标识，同一账户下每个进程的 ID 必须唯一——多个进程使用同一个 ID 会引发断连冲突。默认情况下，TWS 监听端口 7496（实盘）或 7497（模拟盘）；IB Gateway 使用 4001（实盘）或 4002（模拟盘）。

TWS/Gateway API 采用长连接套接字，因此交易系统必须主动检测断开或失效的连接。可以使用轻量级心跳，例如定期调用 `reqCurrentTime()`，并把响应缺失或延迟视为可能影响订单管理的故障。连接中断或 IBKR 报告重置时，应以指数退避方式重连，按需重新订阅市场数据，并重新加载未决订单、已完成订单、成交回报、持仓与账户信息，与经纪商状态对账后再恢复交易。

### 订单类型与执行

IBKR 支持丰富的订单类型。对算法交易而言，最关键的几种是（另见 *第3章*）：

- 市价单立即以最优可得价格成交，但应节制使用——Harris (2003) 论述了市价单如何同时承担价差成本与市场冲击，后者随订单规模相对可用流动性的增大而上升（另见 *第18章*）。
- 限价单指定买入的最高价或卖出的最低价，以牺牲成交确定性换取价格确定性。
- 止损单在触及触发价后转为市价单，适合止损逻辑，但在快速行情中可能造成显著滑点。

IBKR Pro 的 SmartRouting 在多个交易场所间搜寻最优执行，在功能上复刻了机构级的智能订单路由——更关键的是，它不会把订单流出售给批发商。Schwarz et al. (2022) 用 8.5 万笔同步市价单测量了五家美国经纪商的往返执行成本，发现成本离散度介于 0.07% 到 0.46% 之间，而订单流付款（payment for order flow, PFOF）只能解释其中 3.4% 的差异。结论是：经纪商的路由选择，其影响可能超过显性佣金。

IBKR 的自适应订单更进一步：依据市场状况在紧迫性与价格之间取得平衡，正体现了 Almgren and Chriss (2001) 形式化的执行取舍——快速执行可将时间风险降到最低，但会放大市场冲击；缓慢执行能减小冲击，却让头寸暴露于不利的价格变动。

订单属性会进一步改变行为：**取消前有效**（**GTC**）订单跨交易时段保留；**立即成交否则取消**（**IOC**）订单要么立即成交、要么取消；**全部成交或全部不成交**（**AON**）订单不允许部分成交。各类资产可用的丰富订单工具，请查阅 IBKR 文档了解概览。

### 持仓与账户管理

准确的持仓跟踪需要关注几路数据流：

- 持仓更新通过 `position()` 回调送达（经 `reqPositions()` 请求），反映经纪商的权威视图——应在时段开始时以及盘中定期将内部记录与之对账。
- 账户数值（权益、保证金、购买力、盈亏）经 `reqAccountUpdates()` 请求、通过 `updateAccountValue()` 送达；应监控保证金使用率，避免被强制平仓。
- 每笔成交的执行回报经 `execDetails()` 送达，包含价格、数量、佣金与时间——对交易分析与对账至关重要。

### 错误处理

IBKR 的错误信息以数字错误码的形式经 `error()` 回调送达。应实现一个集中式错误处理器，记录所有错误，并把关键错误升级到告警系统——错误往往预示着会随时间恶化的问题。

IBKR 错误码包括：

| 代码 | 含义 | 处置动作 |
| --- | --- | --- |
| 502 | 无法连接 | Gateway/TWS 未运行或不接受连接 |
| 504 | 未连接 | 连接已断开；重连并对账状态 |
| 201 | 订单被拒绝 | 解析消息查明原因（保证金、代码、交易时段） |
| 202 | 订单已取消 | 由客户端或经纪商发起（例如日终取消 GTC 订单） |

### 历史数据访问

IBKR 通过 `reqHistoricalData()` 提供历史 bar（K线）数据，访问可能需要订阅。其限制有若干：

- **限速限制**：历史数据请求受频率限制，具体限额取决于请求模式。应实现带适当延迟的请求排队，而不是假定可以无限速拉取。
- **数据可得性**：历史数据的覆盖因品种和交易所而异。依赖之前先确认数据确实存在。
- **bar 粒度**：可用区间从 1 秒到 1 个月不等，且并非所有品种都提供所有粒度。

对需要大量历史数据的策略，可考虑用专业数据供应商的数据补充 IBKR。IBKR 主要用于获取近期数据，以及与主数据源相互核验。

IBKR 的深度伴随着复杂度。下一节介绍 Alpaca：它通过更简洁的 API 交易更窄的品种范围，是读者初次实盘实验的更快入口。**实现**：参见 `03_ib_paper_trading_demo`，在模拟盘会话可用时，它演示了 IB 连接、预热数据请求和影子模式下的订单流。

## 25.3 集成 Alpaca

Alpaca 提供免佣金的美股、期权与 ETF 交易，以及加密货币市场的 API 接入，采用简洁的 REST 与流式接口，模拟盘访问也十分宽松。对许多读者来说，它是早期实盘实验最省事的经纪商途径。但"**免佣金**"并不意味着零成本：路由质量、价差捕获与交易场所选择仍决定实际执行成本。

Alpaca 还提供付费方案，更侧重执行质量与基础设施，而非零费率的简单性；付费方案同时放宽频率限制并扩大数据覆盖。

### REST 与 WebSocket API

REST API 处理同步操作——提交订单、查询持仓、获取账户信息。流式接口在订阅相关频道后推送异步更新，例如成交、持仓变动和市场数据事件。生产环境中，命令用请求-响应调用，状态更新用持久流。

### 模拟盘模式

Alpaca 的模拟盘无需入金——注册账户、生成模拟盘 API 密钥即可立即开始。模拟环境沿用同样的账户与订单流程，只是模拟成交，而非与真实流动性博弈。因此模拟盘适合集成测试，不适合度量实盘滑点、市场冲击或部分成交行为。

**在投入真实资金之前，务必充分使用模拟盘。** 让完整系统以模拟盘模式运行若干交易时段，确认订单正确执行、持仓准确跟踪、对账如预期运转。

### 与 IBKR 的主要差异

从 IBKR 迁移过来的交易者应注意以下几点差异：

| 对比项 | Alpaca | IBKR |
| --- | --- | --- |
| 品种类别 | 美股、ETF、场内期权、加密货币 | 170 个市场，全品类资产 |

对多资产策略，IBKR 仍不可替代；对大多数交易美股或加密货币的系统化策略，Alpaca 较简单的订单类型已经够用。

**Alpaca 与 IBKR 都通过同一 API 提供加密货币交易**，交易时间 7×24 小时不间断，这要求系统设计支持全天候运行。加密货币案例研究所交易的 19 份 Binance USDT 永续合约中，Alpaca 的美元计价现货子集只覆盖其中 11 种；ADA、APT、ATOM、BNB、COMP、INJ、NEAR 和 SUI 无法在 Alpaca 交易，因此从 Binance 永续标的池移植过来的策略，要么把缺失的标的路由到其他交易场所，要么仅记录信号而不下单。加密货币订单接受小数数量（例如 0.005 BTC）；Alpaca 也支持美股**碎股**。对横跨两类资产的策略，与分别维护多条交易所连接相比，统一 API 简化了集成。**经纪商的产品与服务在不断演变**，务必查阅其网站上的最新信息。

### 直连加密货币交易所 API

对加密货币衍生品——永续合约、期权和杠杆头寸——经由 Alpaca 或 IBKR 的中介接入并不够。主流加密货币交易所（如 Binance、Bybit、OKX 和 Deribit）既充当交易场所又充当对手方，开放提供直接访问订单簿的 REST 与 WebSocket API。这是散户所能获得的最接近直接市场准入的方式，但交易所自身既是撮合引擎又是托管人——这是传统金融中不存在的结构性对手方风险，因为传统金融里经纪商、交易所与清算所是彼此独立的实体。

*25.6 节*的**加密货币资金费率案例研究**部署到 OKX，它是直连交易所 API 的一个典型示例。OKX 的 v5 API 通过一套接口覆盖现货、永续合约、期货和期权，并提供相互独立的实盘与演示（demo）工作流。认证要求、费率表和频率限制都可能变化，因此生产部署应阅读交易场所的最新文档，而不是把从 notebook 得来的运维假设硬编码进系统。

地域限制才是硬约束。交易所的可得性、衍生品准入和杠杆条款因司法辖区而异，且变化频繁。应把交易场所的可用资格当作法律与运维上的前置条件，而不是策略写完后再核对的细节。CCXT 库提供统一的 Python 接口，屏蔽了各交易所特有的认证与限频逻辑，降低了多交易所策略的集成成本。**实现**：`04_alpaca_paper_trading_demo` 演示模拟盘连接与影子模式执行；`05_alpaca_crypto_live_demo` 演示经由 Alpaca API 的加密货币路径；`09_crypto_funding_deployment_loop` 演示 *第12章*资金费率工作流的分场所部署——OKX 提供实时数据（bar 与 8 小时资金费率），Alpaca 加密货币模拟盘在美元计价现货子集上执行。

### 错误处理

Alpaca 的错误以 HTTP 状态码加 JSON 错误体的形式返回：

- **403 Forbidden**：认证失败。核对 API 密钥，并确认模拟盘与实盘密钥与所调用的端点匹配。
- **422 Unprocessable Entity**：订单校验失败。响应体会说明原因——购买力不足、代码无效或市场已收盘。
- **429 Too Many Requests**：超出频率限制。实现指数退避与请求排队。
- **500/503 服务器错误**：Alpaca 基础设施问题。带退避地重试；若持续出现，查看 Alpaca 状态页。

应仔细解析错误响应。`message` 字段通常足以把问题讲清楚，便于确定相应的处置。

### 幂等键

Alpaca 支持客户端自定义订单 ID（`client_order_id`）来实现幂等的订单提交。应充分利用这一特性：

- **生成唯一 ID**：使用 UUID，或基于策略、代码和信号时间戳的确定性 ID。保存内部订单引用与 `client_order_ids` 之间的映射。
- **安全重试**：订单提交超时后，用同一个 `client_order_id` 重试。若原请求已成功，Alpaca 返回已有订单；若已失败，Alpaca 创建新订单。
- **防止重复**：系统绝不应因网络问题或崩溃恢复而产生重复订单。客户端订单 ID 使这一保证成为可能。

这种幂等模式对生产可靠性至关重要，同样适用于 IBKR 集成。

自建并维护经纪商连接并非唯一路径。下一节评估把基础设施、数据和执行打包成托管服务的平台——这是便利与控制之间的取舍，从业者应在选定任一模式前仔细权衡。

## 25.4 QuantConnect 与托管平台

构建并维护交易基础设施需要可观的工程投入。托管平台提供了另一条路：把基础设施交给别人，自己专注于策略研发。构建于开源 LEAN 引擎之上的 QuantConnect 正是这一路线的代表。

### 平台路线与自托管

托管平台打包了基础设施（服务器、网络和监控）、随 API 变化而更新的现成经纪商集成、历史与实时数据源，以及优化过的回测引擎。其取舍在于：便利性与上市速度，对应灵活性与控制力——平台会限制数据源、支持的经纪商和可用订单类型，但大幅减少实现工作量。

本章前几节描述的是另一条路径：用 `ml4t-backtest` 自托管完成研究与验证，再用 `ml4t-live` 以同一策略接口进行模拟盘或实盘执行。这套技术栈让你直接掌控代码、数据流水线和经纪商连接，但也把运维责任留在从业者手中。QuantConnect 与 LEAN 提供一体化的基础设施与托管便利，对周边环境的控制则较少。

### LEAN 引擎概览

驱动 QuantConnect 的 LEAN 引擎是开源的（Apache 2.0 许可证），由此产生了混合选项：

- **云端部署**：把策略部署到 QuantConnect 的基础设施上，按用量付费，享受托管运维。
- **本地开发**：研究阶段在本地运行 LEAN，完全掌控环境，开发期间没有云成本。
- **自托管生产**：把 LEAN 部署到自己的基础设施上——与 QuantConnect 同一引擎，只是运行在你掌控（并付费）的服务器上。

LEAN 支持多种资产类别（如股票、期权、期货、外汇、加密货币）和多家经纪商（包括 Alpaca、IBKR 等）。用 C# 或 Python 编写的策略可以在多年数据上回测，并以极少的代码改动部署到生产。它的主要吸引力在于集成而非极致速度：它把回测、供应商托管数据、经纪商连接和部署基础设施整合进同一个平台。

LEAN 的架构遵循与 *第16章* 讨论过的事件驱动原则类似的设计：数据处理器向算法供给数据，算法生成订单，执行处理器路由给经纪商。框架负责状态持久化、持仓跟踪与对账。

### 取舍——便利性、灵活性与成本

应从多个维度比较平台与自托管系统：

- **开发速度**：平台能加速初期开发——无需搭建基础设施，数据访问预先配置好，还有示例算法可以起步。自托管系统（如 `ml4t-backtest` 加 `ml4t-live` 的工作流）在开始交易前需要更多前期投入。
- **灵活性**：自托管系统可以接入任何数据源、连接任何经纪商、实现任何执行逻辑；平台则把你限制在其支持范围内。策略需要平台不提供的功能时，你将一筹莫展。
- **成本结构**：平台收取订阅费、按算法计费或利润分成。小规模下这些费用不高，大规模下自托管基础设施往往更省。应针对预期的资金规模算出交叉点。
- **知识产权**：在平台上部署意味着策略代码存放在第三方基础设施上。QuantConnect 这类信誉良好的平台实施了访问控制，但风险仍在；自托管系统把策略逻辑留在你自己的基础设施上。
- **运维负担**：平台负责监控、告警、更新和事故响应；自托管系统则需要你自行建立并维护这些能力。

### 平台何时合适

平台适合多种情形：基础设施成本占主导的散户级运营；全力自建之前的快速原型；工程带宽有限、开发时间比运维控制更宝贵的团队；以及通过受支持经纪商交易流动性品种的较简单策略。

在自建基础设施之前，平台也是理解算法交易的有效学习环境。当自定义数据处理或对实盘运营更紧密的控制（包括更低延迟）比托管便利更重要时，自托管技术栈是更好的选择。

### 迁移考量

平台锁定是切实的顾虑。应为可能的迁移早做打算：

- 让策略逻辑与平台特有的样板代码保持可分离，并记录哪些特性可以移植。
- 与数据供应商保持独立合作关系，而不是完全依赖平台数据。
- 有些平台允许导出策略代码——在把迁移当作依靠之前，先测试导出的代码能否在替代基础设施上运行。可考虑跨平台混合运行，或"平台加自托管"的分工，以降低单点故障风险。

无论自托管还是托管，任何实盘系统都必须处理失败的订单、部分成交的订单和乱序到达的订单。下一节把订单生命周期建模为显式的状态机——这一层位于策略信号与经纪商执行之间，无论选择哪条基础设施路径都无法绕开。

**实现**：参见 `06_quantconnect_case_study`，它把 ETF 案例研究的预测导出到 QuantConnect 的 Object Store，并从 LEAN 算法中读取使用。

## 25.5 订单生命周期管理

订单从策略信号到最终成交的旅程包含多次状态转换，其中任何一步都可能失败、超时或产生意外结果。能否正确管理这一生命周期，正是稳健交易系统与脆弱系统的分水岭。典型生命周期的步骤如下：

1. 策略首先基于当前市场数据生成内部目标——"把 AAPL 权重提高到 5%"。
2. 该信号再经仓位规模计算、手数取整和订单类型选择，变成具体订单（"市价买入 150 股 AAPL"）；市价单与限价单之间的选择，正体现了 Almgren and Chriss (2001) 形式化的紧迫性与冲击之间的取舍。
3. 订单被发送给经纪商，但在确认回执到达之前，它的存在状态并不确定——提交过程中的网络故障会让你无法断定订单是否到达了经纪商。
4. 经纪商确认收到并分配订单 ID 后，订单即在交易所生效等待成交。
5. 执行可能立即完成（流动性好的股票上的市价单），也可能延后（偏离市场价格的限价单），部分成交会产生中间状态。Madhavan (2002) 为决定执行质量的微观结构动态提供了完整框架。
6. 成交之后，内部持仓记录随之更新，对账确认与经纪商记录一致。

每一步都可能出故障。稳健的系统会及早发现故障并妥善应对，而不是任由未被察觉的差异不断累积。

### 订单状态的状态机

状态机把一个过程表示为一组离散状态，加上规定事件如何触发状态间有效转换的规则。用它为订单生命周期建模是一种纪律化的做法，因为每个实盘交易系统都必须准确知道每笔订单处于什么状态、此时哪些事件是有效的、哪些操作不再被允许。**七个主要状态**是：

1. *已创建*（Created）：仅存在于内部，尚未提交。
2. *已提交*（Submitted）：已发送给经纪商，等待确认回执。
3. *已确认*（Acknowledged）：经纪商确认收到，订单生效等待成交。
4. *部分成交*（Partially Filled）：部分数量已成交，其余仍在等待成交。
5. *已成交*（Filled）：全部成交，终结状态。
6. *已取消*（Canceled）：全部成交之前被撤销，终结状态。
7. *已拒绝*（Rejected）：经纪商拒绝受理，终结状态。

*图 25.2* 可视化了包含 10 个状态的完整状态机及其间的有效转换。**终结状态**（Filled、Canceled、Rejected）没有出边，生效中的状态则可以通过成交或取消继续推进。不妨注意，这与 *第3章* 分析过的 NASDAQ ITCH 订单流消息的逻辑何其相似。

*图 25.2：订单状态机。显式的生效中状态与终结状态让异步的经纪商回调可审计，并约束合法的状态转换*

该状态机是 *25.1 节*统一框架与 *25.2–25.3 节*经纪商 API 之间的关键集成点。

模式有两种：

- 在**回测模式**下，框架瞬时模拟状态转换。
- 在**实盘模式**下，同一个状态机处理异步的经纪商回调。

由于两种模式共享状态机逻辑，订单处理行为可以在回测中验证，并在生产中原样复现。状态转换必须处理以下边界情况：

- **乱序消息**：成交通知可能先于确认回执到达。状态机必须无论消息先后顺序如何都能接受有效转换。
- **并发事件**：订单恰好在成交的同时收到撤单请求，会形成竞态。撤单在途期间，订单进入 `PENDING_CANCEL`；随后成交通知先于撤单确认到达，在途的撤单被丢弃，审计轨迹记录下 `PENDING_CANCEL` → `FILLED` 的转换，使整个处理过程事后仍可重构。
- **网络超时**：超过时限仍未收到确认的提交，需要先查询经纪商状态，再决定是否重试。

### 部分成交、拒绝与取消的处理

**部分成交**需要持续计算：累计成交量、跨各笔成交的成交量加权平均价，以及剩余数量。每个成交事件都会触发持仓更新，若策略以特定仓位规模为目标，还可能触发新订单。

**拒绝**需要弄清原因。购买力不足？等其他订单释放资金后重试。代码无效？记录错误并排查。市场已收盘？等开盘再说。切莫盲目重试被拒订单。**取消**可能由交易员发起，也可能由经纪商发起。日终取消当日有效订单属正常现象；经纪商在盘中取消订单则说明有问题，需要调查。

### 日终对账

每日对账将内部记录与经纪商对账单相比对：

- **持仓对账**：内部持仓数量与经纪商报告的持仓相对照。差异意味着存在漏记的成交、错误的计算，或在系统之外发生的交易。
- **订单对账**：内部未决订单列表与经纪商未决订单相对照。经纪商侧的"孤儿订单"（内部未跟踪）非常危险——它们可能随时成交。
- **资金对账**：预期现金余额与报告余额相对照。差异意味着存在漏记的成交、费用计算错误，或在系统之外发生的存取款。

一旦对账发现差异，应暂停自动交易，直到差异解决。自动修正可能把记账错误变成交易错误；调整前先做人工核查更安全。

### 崩溃恢复的幂等性

系统崩溃会造成一种尤其危险的故障模式：系统提交了订单，却在记录这次提交之前崩溃。重启之后，还要不要重新提交？

**客户端订单 ID** 解决了这个问题。提交之前，为订单生成并持久化一个唯一 ID，并把它包含在提交请求中。恢复之后：

1. 检查该订单 ID 是否已存在于未决订单中。
2. 用客户端订单 ID 查询经纪商。
3. 若经纪商已有该订单，则更新内部状态使其一致。
4. 若经纪商没有，则说明提交失败；用同一个 ID 重试。

这一模式确保订单绝不因崩溃而重复。客户端订单 ID 充当幂等键——同一 ID 提交两次会返回已有订单，而不是创建重复订单。

正确的订单处理是必要条件，但并不充分——整条信号生成流水线还必须在回测与实盘两种模式下产生完全相同的输出。下一节建立一套系统的验证方法，从原始数据到最终订单的每个阶段都检验一致性。

**实现**：notebook `07_order_state_machine` 实现了 10 个订单状态和 19 条有效的状态-事件转换，并通过审计轨迹演示完整的生命周期跟踪。

## 25.6 通过流水线验证确保技术一致性

实盘交易的失败有两种不同来源：

- 第一种是*技术性失败*：流水线偏离了回测，相同输入产生了不同输出。这是 bug，应当在部署之前就被发现。
- 第二种是*统计性失败*：流水线在技术上完全正确，但样本外表现与回测不符，原因是市场变了，或者回测过拟合。

Bailey et al. (2015) 提供了估计回测过拟合概率的框架（*第16章*已有讨论），但即便那一分析也以技术一致性为前提。本节讨论一致性；*第26章*讨论一致性验证完成之后所需的持续监控。

技术一致性验证确保实盘系统做的正是回测所模拟的。在验证一致性之前，实盘表现的偏差可能来自 bug，也可能来自市场状况——让人无从诊断。

### 验证方法

验证沿信号生成流水线逐步推进。在每个阶段，向回测系统与实盘系统喂入完全相同的输入，然后比较输出。任何差异都意味着存在需要排查的技术性差异。

*图 25.3* 展示了并行的回测与实盘流水线，每个阶段都设有比对检查点，从而可以对差异做二分查找：当输出不一致时，逐个检查中间阶段，隔离差异的来源。

![图 25.3](assets/figure_25_3.png)

*图 25.3：流水线验证流程。逐阶段比较原始数据、特征、预测、信号与订单，在实盘资金承担风险之前隔离技术性差异*

典型 ML 策略的流水线阶段：

1. **原始数据 → 特征**：市场数据转换为模型特征。基于复权收盘价计算的动量因子，无论在回测回放中还是在实时数据快照上计算，都应得到相同的值。
2. **特征 → 预测**：对基于 ML 的策略，模型把特征转换为收益预测。同一特征向量在两个环境中必须产生相同的预测。
3. **预测 → 信号**：预测与风险模型、约束条件相结合，产生目标持仓。给定相同的预测和当前持仓，优化器应输出相同的目标。
4. **信号 → 订单**：目标持仓转换为实际订单，需考虑手数、既有持仓和执行约束。同一信号应生成相同的订单。

应力争每个阶段都有自动化测试，以验证流水线完整性并识别回归。

### 特征一致性测试

特征验证使用时点正确（point-in-time, PIT）的历史数据。选定一个历史决策日期，把回测运行到该时点，提取该时间戳计算出的特征值，把相同的 as-of 原始数据喂给实盘特征流水线，然后比较得到的特征向量。

差异暴露实现上的分歧。常见元凶包括：

- **回测中的前视偏差**：回测不小心用到了决策时点尚不可得的未来数据，而实盘系统正确地只使用过去数据，算出的特征便不同。López de Prado (2018) 将前视偏差列为夸大表面业绩的关键回测陷阱。
- **数据复权差异**：回测全程使用拆股复权后的数据，实盘系统收到的却是未复权价格，可能出现复权历史中不存在的价格跳变。
- **缺失数据处理**：回测对缺失价格做前向填充；实盘系统却报错、采用别的填充方法，或干脆把缺失值直接传给模型。
- **时区混乱**：回测按一个时区解释时间戳，实盘系统用的却是另一个。

**创建跨多个历史日期验证特征一致性的自动化测试**，并持续运行——数据源变更、库升级或代码修改都可能引入差异。

### 预测一致性测试

对 ML 策略，要验证训练好的模型在两个环境中产生完全相同的预测。从回测中某个具体历史时点提取特征向量，把同一向量分别在回测环境和生产环境中过一遍模型，直接比较输出。模型差异的来源包括：

- **序列化差异**：研究环节保存的模型在生产环境中反序列化后并不完全一致。库版本不同、依赖缺失或平台差异都可能造成细微变化。
- **预处理不匹配**：生产流水线应用预处理（缩放、编码）的方式与研究环节略有不同。
- **随机状态**：若模型是随机的，确保生产使用相同的随机种子或确定性模式。
- **数值精度**：用 float32 而非 float64 计算，微小差异会在深层网络中不断累积。

同样，应为模型预测工作流建立自动化测试，及时捕捉偏差。

### 仓位规模逻辑验证

仓位规模确定与投资组合优化带来额外的复杂度。给定相同的预测和当前组合，在两个环境中分别运行优化器，直接比较目标持仓。

差异来源包括：

- **优化器配置**：约束容差或求解器设置的细微差别会得出不同的最优点。
- **风险模型差异**：使用不同的协方差估计或风险因子载荷会改变最优持仓。
- **标的池差异**：受数据可得性或上市状态影响，回测与实盘系统操作的标的池不同。

### 自动化回归测试

用自定义测试套件自动完成验证，而不是依赖人工抽查。例如对日频策略，系统应在每天早晨核对：前一天的实盘信号是否与回测基于同一信息集会产生的结果一致。任何不匹配都应暂停交易，直到得到解释。

部署之前，每次提交都应运行测试，将特征与预测和一组基准真值用例比对。此外，应定期在历史数据上完整回放实盘流水线，并与回测结果对照，以捕捉单元测试可能遗漏的集成错误。

`08_pipeline_verification` 测试装置把这一纪律落到了实处：在确定性测试记录上，五项门控一致性测试端到端通过（特征、预测、信号、订单数量、订单明细）；特征数量标注为 `EXPECTED_DIFFERENCE`，使预热窗口不匹配只作为提示信息呈现，而不会让 CI 门禁失败；跳过的测试数为零，因为当异步实盘流水线无法运行时，测试装置会显式发出 SKIP 语义——堵死了"对着空实盘日志静默通过"这一失败模式。

### 诊断差异点

测试发现差异后，诊断应沿流水线系统推进。先验证输入完全相同——数据源问题很容易被误认成计算 bug。若端到端输出仍不一致，再逐阶段比较中间产物。

特征一致而预测不同，指向模型层；预测一致而信号不同，指向优化层。此外还要检查依赖版本，库升级可能改变边界情况下的行为。在每个流水线边界记录输入与输出，能显示两个环境最早在哪里出现分歧，从而加快诊断。

### 统一数据源

一个隐蔽却关键的差异来源是**交易所层面的差异**。用一个交易所的历史数据训练，却在另一个交易所上跑实时推断，会产生代码验证无论如何都检测不到的分布偏移：

- **报价惯例不同**：买卖价差、价格取整和时间戳对齐方式因交易所而异。用 Binance 历史数据计算的特征，与用 Coinbase 实时数据计算的同一特征，分布性质可能略有不同。
- **费用结构影响信号**：各交易所数据中蕴含的交易成本不同。基于交易所 A 的资金费率结构训练出的资金费率信号，未必能泛化到计算方法不同的交易所 B。
- **流动性特征各异**：成交量形态、市场深度和订单流特征因交易所而不同。按成交量给资产排序的横截面特征，在不同交易所可能给出不同的排名。

首选方案很直接：训练与推断使用同一个交易场所。把一个交易所的历史数据与另一个交易所的实时数据混用，会引入分布偏移。当无法匹配场所时，就把这种不匹配当作一个明确的验证问题来处理。加密货币永续合约的素材正说明了这一现实难题：*第12章*的模型产物植根于 Binance 来源的训练数据，而实盘部署演示连接的却是 OKX 市场数据。于是，场所比较成了验证任务的一部分：特征定义可能一致，交易所惯例却仍有差异。运维层面的教训是：差异必须在实盘部署之前度量并记录在案。

历史数据深度可能迫使你做出务实的选择——单一交易所的公开 API 也许只提供 90 天历史，而存档数据集则有多年数据。混用数据源时，先验证特征分布具有可比性，再在合并数据上训练。

### 资金费率策略——实盘部署

**加密货币永续合约案例研究**展示了从 ML 到实盘的完整流水线。*第12章*的 LightGBM 分类器使用 13 个特征：三个资金费率特征（溢价 z 分数、8 小时动量和 24 小时动量）加十个辅助价格特征，覆盖多个周期的动量、滚动波动率和技术指标。核心假设——极端资金费率反映了易于均值回归的拥挤持仓——详见 *第6章*（另见本书 GitHub 仓库）；这里的重点是把训练好的模型部署进实盘执行工作流。实盘交易中，notebook 部署到 OKX：它按 8 小时结算周期提供实时资金费率数据，提供分钟级与小时级的 OHLCV K线，且数据获取与订单执行的 API 都易于访问。

实盘流水线每分钟执行：

1. *拉取* OKX 的小时级 bar 与资金费率历史。
2. *计算*全部 13 个特征，在实盘场所允许的范围内尽量贴合训练时的数据结构与变换。
3. *预测*：使用训练好的 LightGBM 分类器（三分类：`stop_loss`、`timeout`、`profit_take`）。
4. *决策*：根据预测概率决定进场、持有或退出。

两套退出机制保护资本：

- **预测翻转退出**：当 P(profit) 跌破退出阈值，表明资金费率机会已经关闭或条件已变化时，退出持仓。
- **止损退出**：若价格逆向变动超过（例如）1%，无论模型预测如何，立即退出。

这一架构表明，只要特征计算保持一致（但预测表现可能有差异），ML 模型可以部署在比训练目标更高的频率上。这正是本章的核心原则：同一套特征定义必须经受住从研究到推断的转换。本节前文介绍的验证套件提供了系统性确认这种一致性的工具。

### 一致性与市场状态稳定性

技术一致性是本章的主要关切：实盘流水线必须计算出与回测完全相同的结果。但即便通过了一致性验证，若训练之后市场结构发生变化，流水线仍可能亏钱。加密货币资金费率案例直接说明了这一区别。

研究环节在 2020–2023 年数据上训练 LightGBM 分类器，并在延伸至 2025 年的验证窗口与留出集窗口上评估。验证集表现显示出正的优势；留出集表现——其中包含 2025 年末的加密货币回撤——却没有。直觉反应是怀疑存在 bug——某种细微的特征漂移或泄露。本节的验证纪律排除了这一可能：特征、预测和信号在各环境间完全匹配。

解释是结构性的。资金费率信号规定了一种特定的横截面配置：做多资金费率异常为负的代币（空头显得拥挤、预计将均值回归上行），做空资金费率异常为正的代币。在案例研究由 19 份永续合约组成的标的池中，这一配置把多头腿压在市值较小的代币上（COMP、DOT、SUI、AVAX），各约 10% 权重，把空头腿压在主流币上（BTC、ETH）。当 2025 年的回撤压缩整个加密资产类别时，山寨币多头腿的回撤远超主流币空头腿的收益。信号本身内部依然自洽；是隐含的因子暴露（做多山寨币、做空主流币）转向了不利于策略的一边。留出集的亏损分散在整个多头腿上，而不是集中在少数几只爆仓币上：亏损贡献前三的代币合计仅占总亏损的 8% 左右。标的池过滤——例如把标的池限定为主流币——解决不了这个问题：去掉山寨币多头腿会留下一个没有对冲的空头头寸，那就不是信号所规定的策略了。

下面划清 *第25章* 与 *第26章* 的职责边界：

- *第25章*问的是：实盘系统计算的量与回测相同吗？就本例而言，相同。
- *第26章*问的是：鉴于当前的市场状态特征，系统还应继续交易吗？这是一个监控问题——跟踪资金费率均值、横截面离散度和已实现相关性是否仍与训练分布相似——即便流水线技术上完全正确，它也可能触发暂停。

因此，本章的 OKX 演示把加密货币流水线当作一件一致性验证产物，而不是一个盈利策略。这个演示的价值在于它暴露了实盘交易的每一个机制：需要认证与无需认证的端点、异步数据源编排、从训练模型到订单的通路，以及在不利盈亏条件下熔断开关的行为。至于当前的资金费率状态是否还眷顾该信号，那是另一个问题，本章不试图回答。

### 对照部署——外汇日频信号

外汇案例研究提供了一个对照。其留出集表现与验证集保持一致——没有符号翻转，也没有在样本外窗口内转向不利于策略的集中单一宏观因子暴露。其实盘部署特性也较为宽容：日频决策节奏、点差狭窄的报价驱动型交易场所，以及通过 Interactive Brokers 模拟账户上的 IDEALPRO 通道即可获得的连续工作日市场。

外汇 notebook 把 *第12章* 的外汇模型接入一个模拟盘循环，每日在主要货币对与套息交叉盘之间再平衡。验证纪律依然适用——由实时 tick 数据计算的特征必须与回测由日终 bar 计算的结果一致——但市场状态稳定性不再是主要担忧，因为策略隐含的因子暴露（套息与短期动量的混合）与单一的全市场回撤耦合较弱。

两个演示合起来，勾勒出一致性的两面：

- OKX 部署展示了：即便市场状态不再眷顾信号，流水线也能安然完成从研究到推断的转换。
- IB IDEALPRO 部署展示了：当流水线与市场状态相互配合时，实盘执行是什么样子。

第三个演示把一致性讨论延伸到**篮子再平衡**场景。IB 篮子再平衡 notebook 按 20 日动量信号对 20 只美股大盘股组成的标的池排序，并通过单一 `IBBroker` 模拟会话路由生成的篮子。其中两个设计选择值得点出，因为它们恰恰是实盘部署才会暴露的那类一致性缺口：

1. **预热 bar** 通过 `IBBroker.reqHistoricalDataAsync` 拉取，而不是用研究阶段的加载器，从而让排序输入和 `SafeBroker` 的订单金额参考价来自将要执行订单的同一会话。若用研究阶段的加载器，就有按陈旧价格排序、按历史价位计算仓位规模的风险，导致特征一致性失败。代价在运维层面：IB 的限速和按合约的资格认证给预热步骤增加了延迟，需要用 `asyncio.gather` 并行化逐标的的请求。
2. **提交后的状态**通过轮询 `IBBroker.get_positions_async` 对账，而不是订阅 `ib.execDetailsEvent`。轮询更简单，对每日再平衡也足够，但会引入延迟，且可能漏掉落在轮询间隔之间的成交；事件驱动的对账才是生产级方案。

这两个选择都在 notebook 中有说明，让你看到取舍本身，而不是绕过它。

技术一致性是前提，但通过验证的流水线仍需要运维纪律才能在生产中存活。下一节给出预检清单、熔断开关和分级部署流程，在技术一致性确认之后保护实盘资金。

**实现**：`08_pipeline_verification` 使用确定性一致性测试装置与实盘封装器，测试特征、预测和信号的一致性。

`09_crypto_funding_deployment_loop` 是加密货币永续合约上从 ML 到实盘的完整流水线——在 *第12章* 的资金费率面板数据上训练 LightGBM 三分类方向模型，从 OKX 公开 API 拉取实时 OHLCV bar 与 8 小时资金费率，对全部 19 份永续合约打分，并把生成的篮子经由 Alpaca 加密货币模拟盘路由到 Alpaca 上架的 11 个美元计价现货交易对（其余永续合约仅记录信号不下单；需要 Alpaca 账户）。

`11_fx_deployment_loop` 是单一场所的对照：在 *第12章* 的 20 个货币对外汇面板上训练 Ridge 回归器，通过 Interactive Brokers 模拟账户部署在 IDEALPRO 上——IB 同时充当实时数据平面（经 `reqHistoricalDataAsync` 获取每日外汇 bar）与执行平面（外汇现货订单），因为外汇是少数能由单一散户经纪商同时覆盖两者的资产类别之一（需要 IBKR 账户）。

`12_ib_basket_rebalance_demo` 把讨论延伸到 IB 实盘模拟的篮子再平衡场景，其启动对账模式将在 *25.7 节*再次被引用。

## 25.7 运维就绪

通过全部验证测试的系统，仍可能因运维疏漏而在生产中失败。本节介绍上线前的要求与持续的实践，正是它们把可靠交易与灾难性意外区分开来。

### 预检清单

运维就绪始于启动门禁，而不是第一条信号。在允许策略交易之前，必须通过以下检查：

1. **运行时环境**必须证明容器或服务器健康、到经纪商的网络路径畅通、数据源是最新的，且数据库和监控等支撑服务可用。从半降级环境中启动的策略，在发出第一笔订单之前就已处于异常状态。
2. **认证是另一道门禁**。凭据必须有效，模拟盘或实盘的设置必须与目标环境一致，账户必须拥有计划中的订单和数据源所需的权限。这类检查在 notebook 里容易被忽略，因为凭据缺失通常会大声报错；生产中更危险的是部分成功——会话认证通过了，却连到错误的账户、错误的环境，或只有受限的权限集。
3. **交易算法的状态必须自洽**，交易才能开始。内部持仓应与经纪商持仓一致，现金余额应能对上，上一会话不应残留孤儿订单，上一轮对账应干净完成。没有这个基线，策略就不再是延续昨天的状态，而是在叠加一个未知的差异。
4. **市场环境**属于同一道启动门禁。系统应确认交易场所在需要时处于开盘状态、交易所没有激活限制措施或熔断机制，且价格是最新的而非过期的。
5. **配置**也在门禁之列：风险限额、订单规模上限和熔断开关的访问方式，都应在第一笔自动操作之前核验完毕。

这些检查应在启动时自动运行，输出一份简短的人类可读报告，并在任一必要条件不满足时阻止交易。

### 熔断开关与紧急程序

验证能降低风险，但不能免除人工干预的需要。当系统行为异常时，**响应应当分级**：

- 第一级：暂停新信号，让既有订单自然了结。行为可疑但尚未明确危险时，这是正确的响应。
- 第二级：撤销全部未决订单，持仓保持不变。订单路由或订单逻辑可疑、但现有头寸尚可接受时，这是合适的做法。
- 第三级：清空持仓，把组合变现为现金。当对系统状态的信心已不足以证明继续持有风险的合理性时，这是正确的选择。
- 最后一级：完全关闭交易进程及所有依赖它的自动化。这一级留给基础设施故障、状态损坏，或操作者对系统的信任彻底崩溃的情形。

每个动作都应能通过单一明确的控制触发：一条命令、一个快捷键或一个经过测试的按钮。高压之下，多步骤的应急程序会失灵，因为它要求操作者在系统最不可信的时刻保持清晰思考。熔断开关还应独立于它所控制的组件：若策略引擎挂起，操作者仍需要一条经纪商侧或基础设施侧的路径来撤单和清空风险。

### 实盘运行时的强制安全

这些预检要求并非纸上谈兵。在 `ml4t-live` 中，`SafeBroker` 是强制执行这些要求的唯一关口，运行时会区分"仅写入文档的限额"与"真正生效的控制"。持仓市值上限、单笔订单上限、日亏损熔断开关和最大数据过期阈值，都会在每笔订单意图到达经纪商适配器之前接受检查；任何一项会被突破的订单都会抛出异常，而不是被发出。

其中两项控制值得专门关注，因为一旦缺乏持久化，它们在故障时会退化为放行（fail open）：

- **日亏损熔断开关**只有挺过交易日内的引擎重启才有用；否则，一次崩溃加重连就会重置亏损计数器，在最糟糕的时刻重新放行交易。`SafeBroker` 在每次状态转换时把日亏损状态写入状态文件，并在重连时重新加载，因此当日重启能带着完好无损的熔断开关状态继续运行。
- **数据过期检查**同样如此：它要求记录每个资产最近一根 bar 的时间戳；引擎维护这一按资产的快照，对最新市场数据超过配置阈值的订单一律拒绝。

这两项合起来防住了实盘交易最常见的两种失败模式：在交易场所故障期间对着过期数据源继续交易，以及在熔断开关本应锁定之后重新建仓。

**启动对账**补上了常见失败模式的第三块拼图。`SafeBroker.connect()` 运行时，会把上一会话持久化的快照——引擎上次关闭时所知的持仓与未决订单——与经纪商当前的权威状态做比对。报告干净意味着两者一致；报告不干净则说明会话之间发生了变化：一笔盘后订单最终成交了、有人在图形界面里手动清了仓、一笔订单在系统之外被取消，或一笔部分成交落在最后一次持久化之后。对账报告会暴露给调用方，任何生产级启动器都应拒绝开始新的交易周期，直到报告干净，或操作者已显式重置持久化状态。`12_ib_basket_rebalance_demo` 原样遵循了这一模式。

`02_etfs_deployment_loop` 的部署循环额外维护两条运行时会检查、却无法从配置推断的不变量。**训练截断守卫**把 `LABEL_AVAILABLE_AS_OF` 固定为 `LIVE_WINDOW_START − forward_horizon_days`，确保没有任何 `fwd_ret_h` 训练标签读到实盘窗口内的价格——2025-01-01 实盘窗口上的 21 天前瞻收益，会把训练截断强制定在 2024-11-29 而不是 2024-12-31。`feature_cutoff_date` 与 `label_available_as_of` 连同运行记录一起持久化在 `training_metadata.json` 中，*第26章*的监控循环因此可以事后审计这一不变量，而无需重新训练。**篮子处置**则拆分为 `intended_basket`、`attempted_basket`、`accepted_basket` 和 `failed_basket` 四部分，每次运行分别持久化，而不是压缩成一个状态字符串。*第26章*的监控器在 `failed_basket` 非空时告警，无需重新解析执行记录；本章 CI 使用的干跑路径（`SUBMIT_PAPER_ORDERS=false`）把完整篮子保留在 `intended_basket` 中，因此即使没有实盘经纪商，处置结果本身也保持可测试。

与经纪商无关的操作界面来自 `ml4t-live` CLI：

- `ml4t-live status` 读取持久化状态文件，报告当前日亏损计数器、熔断开关锁存状态、持久化的持仓快照，以及上一会话所知的未决订单。
- `ml4t-live shadow <strategy>` 以影子模式限时运行某策略，风险面相同但成交为虚拟，并报告一小组健康状态：
- `ok`：bar 正常到达时。
- `waiting_for_data`：第一根 bar 到来之前。
- `feed_silent`：bar 在配置的静默窗口内停止到达时。
- `idle_market_closed`：预期没有新数据时。
- `broker_disconnected`：经纪商连接已断开时。

这里列出的状态是看门狗或监督进程应当*消费*的信号；它们不能取代看门狗本身。

### 从模拟盘过渡到实盘

模拟盘验证的是集成，但不能验证市场冲击、实盘佣金，或真金白银带来的运维压力。在 ML4T 技术栈中，这一过渡从 `ml4t-live` 的影子模式或模拟盘模式开始，使用通过回测验证的同一套策略逻辑。合理的过渡从一个足够长的模拟盘阶段起步，长到足以观察日常行为：订单应正确路由，对账应每日通过，策略与经纪商之间不应出现无法解释的漂移。

首次实盘部署只应动用计划资金的一小部分。目的不是证明盈利能力，而是验证在资金真正承担风险时，实盘成交、费用和持仓更新是否如预期运作。若该阶段保持干净，可以逐步增加资金。规模每上一级，都是对策略能否在更高赌注下保持运维稳定的新一轮检验。

并行运行能让这一过渡提供更多信息。让实盘与模拟盘版本并排运行，或在执行账本之外保留一个影子组合，可以暴露信号、订单时序和实际成交上的差异。在过渡窗口内，这些差异在诊断上往往比任一账本的原始盈亏更有用。

### 监管与辖区考量

实盘交易意味着与受监管的金融市场打交道。算法交易的规则因辖区而差异巨大，有志于交易的人必须在部署任何自动化系统之前，弄清其运营环境所适用的要求。本节概览截至 2026 年初的监管图景，仅为实务参考，不构成法律意见。

#### 美国

美国对通过经纪商运行算法策略的散户个人没有特别的注册或审批要求。不过，有几条规则塑造了实际环境：

- **典型日内交易者规则（Pattern Day Trader rule）**要求在 5 个交易日内执行 4 次及以上日内交易的账户保持至少 2.5 万美元的最低权益——对运行日内策略的小账户而言，这是一项硬约束。
- **SEC 规则 15c3-5（市场准入规则）**要求券商对所有订单——无论手动还是算法——实施交易前风险控制，实际上禁止了未经过滤的"裸"市场接入。
- **FINRA 规则 3110** 对券商课以监督义务。对本书的大多数策略——通过标准经纪商 API 以日频或更低频率再平衡——这些规则基本是透明的：经纪商的基础设施负责交易前检查，仓位规模也远低于触发强化审查的阈值。

#### 欧盟

**MiFID II 第 17 条**要求从事算法交易的投资公司向本国主管当局报备，维持有效的风险控制，并确保交易系统具备适当的阈值与限额、足够健壮。公司必须实施交易前控制，包括价格上下限（price collar）、最大订单金额和紧急终止按钮（kill button）。

**这些义务适用于受监管的投资公司**，而非通过持牌经纪商交易的散户个人。然而，散户交易者一旦扩张到管理外部资金，就会进入受监管领域并面临监管要求。

#### 印度

印度已走向最详尽的散户算法交易监管制度之一。SEBI 和交易所现在对许多散户自动化部署要求经纪商中介的审批流程和由交易所分配的标识符。

具体操作细节屡次变更，因此针对印度市场的策略应在上线前直接对照经纪商与交易所的最新指引核实，而不是从过时的博客文章或示例代码中推断。

#### 交易税与准入限制

在正式审批之外，地理位置还决定了交易成本与产品可得性，其影响可能压倒其他一切考量。交易税、杠杆上限和交易场所准入，可以把一个原本诱人的回测变成无法交易的策略。英国印花税、欧洲金融交易税和产品层面的加密货币限制都是常见例子。加密货币永续合约策略与美国 ETF 轮动策略面对的法律与经济约束并不相同，哪怕两者的实现看起来非常相似。

法律体系本质上以国家为单位，因此不存在全球通用的解决方案。把任何策略部署到实盘之前，先在目标辖区核实四件事：

1. 该产品交易是否合法。
2. 经纪商是否支持对它的自动化接入。
3. 适用哪些税费或市场准入费用。
4. 账户受哪些杠杆或保证金规则约束。

这些检查应写进部署清单，而不是等策略已经建成之后再补进附录。

### 向第26章移交监控

系统上线并通过技术验证后，核心问题随之改变。问题不再是代码是否按设计运行，而是实盘表现是否保持在预期之内、输入分布是否保持稳定、模型行为能否长期保持可解释。*第26章*讨论监控与适应问题。

**实现**：

- `10_safety_risk_demo` 单独走查可配置的风险面——订单与持仓上限、限流、手动熔断开关、经 `VirtualPortfolio` 的影子模式订单路由，以及资产限制过滤器。
- `12_ib_basket_rebalance_demo` 把同样的控制带进 IB 实盘模拟会话，并落实启动对账模式：在篮子循环之前调用 `SafeBroker.connect()`，且只要对账报告不干净，notebook 就拒绝启动。
- `13_runtime_safety_showcase` 在故障条件下演练相应的运行时信任契约：`MarketSnapshot` 超过配置阈值后的过期数据拒绝、模拟日亏损突破时熔断开关自动激活且锁存状态在 `SafeBroker` 重建后依然保留、由故意分歧的持久化状态文件生成的不干净 `reconciliation_report`，以及上文叙述的 `LiveEngine` 健康状态转换。

## 25.8 总结

本章讨论了算法交易中最常见的失败模式：回测系统与实盘系统之间的技术性差异。统一框架模式——同一策略代码在两种模式下原样运行——从构造上消灭了整整一类 bug。我们集成了三种取舍各异的执行模式：Interactive Brokers 提供具备 SmartRouting 与组合保证金的专业级全球接入；Alpaca 面向开发者，覆盖美股与加密货币交易；直连加密货币交易所 API 则服务于需要场所级接入的衍生品策略。经纪商选择本身就是一项执行质量决策——路由架构对实际成本的影响超过挂牌佣金——而产品可得性、交易税和杠杆上限等地域约束，进一步决定了什么可以部署在哪里。托管平台为优先考虑便利而非完全掌控的交易者提供了第四条路径。

在执行一侧，我们把订单生命周期建模为有 10 个状态和 19 条有效转换的显式状态机，通过幂等的客户端订单 ID 处理部分成交、竞态条件和崩溃恢复。流水线验证——对回测与实盘系统的特征、预测和信号做系统性一致性测试——确保实盘交易失败的第一类（技术性 bug）在部署之前就被发现。运维就绪流程——从四级熔断开关到循序渐进的模拟盘转实盘过渡——提供了生产运行所需的纪律。上线是一项成就，但它也是新挑战的开始：市场会变，模型会衰退。*第26章*讨论维持长期业绩所需的监控与适应基础设施——漂移检测、熔断机制与安全的模型发布。
