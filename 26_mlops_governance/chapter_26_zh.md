# 第26章：MLOps 与治理

一个模型闯过了所有回测，*第25章*所述的部署验证也让系统正式上线，用真实资金执行真实交易。接下来的问题是：如何让它持续正常运转。

每一个上线的模型都会衰减。市场状态会变，竞争对手会发现相似的信号，模型学到的统计关系会逐渐被侵蚀。一套交易业务是盈利还是毁灭资本，往往取决于我们多快发现这种衰减，以及响应有多稳妥。

本章构建部署之后的基础设施，正是它把生产级交易系统与研究原型区分开来。*第25章*确保了系统正确启动，如今的任务则是让它保持正确，或者在无法保持时体面地失效。治理模型分三层：检测，依靠数据校验门禁、滚动指标和漂移分析；响应，依靠影子评估和分阶段上线；自动化安全，依靠熔断机制在亏损或市场条件越过限额时停止交易。至于配套的 MLOps 基础设施——特征存储、模型注册表、CI/CD 等——应按团队成熟度适度配置，而非全盘照搬。

完成本章学习后，你将能够：

- 区分技术性的流水线分歧与统计性的绩效衰减，并选择相应的诊断与响应工作流。
- 构建一套实盘监控框架，综合数据完整性门禁、滚动绩效指标、回测-实盘对比与执行质量检查。
- 对生产产物应用漂移诊断，包括 PSI、K-S、基于 SHAP 的特征监控，以及自适应窗口（ADWIN）与漂移检测方法（DDM）等在线检测器。
- 设计安全的模型更新工作流：影子模式、现任模型与候选模型的对比评估、明确的晋级标准、分阶段上线门禁，以及经过测试的回滚流程。
- 在交易、策略、组合和系统四个层级实现多级熔断，并配套明确的恢复与人工接管纪律。
- 评估并适度配置配套的 MLOps 技术栈，包括特征存储、数据版本控制与血缘、模型注册表、实验跟踪和 CI/CD 控制。

*26.1 节*的"技术性失效对统计性失效"分类法统领全章结构：检测（*26.2 节*与*26.3 节*）、响应（*26.4 节*）、自动化安全（*26.5 节*），以及配套的 MLOps 基础设施（*26.6 节*）。

监控、漂移和上线相关的 notebook 全部基于真实的案例研究产物：`us_equities_panel` 的留出集边界、存储下来的预测流、真实的特征面板，以及记录每次训练运行的 SQLite 注册表。熔断器 notebook 用 SPY 在 2020 上半年穿越新冠疫情暴跌的真实行情来驱动其市场风险规则；只有基础设施延迟流仍是合成的，其范围经过裁剪，以便让延迟熔断器滚动平均值的触发过程可供检视。其余基础设施 notebook 则操作同样的本地 Parquet 与 SQLite 存储。券商连接不在讨论范围内；告警逻辑、数据血缘和晋级门禁均以实际工作流输出为基础。

## 26.1 实盘交易的两类失效来源

实盘交易的失效分为两类，需要不同的诊断与响应。混为一谈只会浪费时间和资本。

### 流水线分歧导致的技术性失效

*技术性*失效是指实盘系统的计算方式与回测不一致。同样的输入本应产生同样的输出，实际情况却并非如此。常见原因包括：数据格式不匹配（回测用的是复权价格，而实时数据源提供的是未复权价格）、时序误差（回测中在收盘时刻计算的特征，在生产环境中会稍有延迟地到达，于是"20 日波动率"覆盖的窗口并不相同），以及实现缺陷（比如正负号写错、索引差一，或者漏掉一步归一化——它不会报错，却会悄悄产生错误的结果）。

技术性失效属于*验证问题*。*第25章*已经处理过这类问题：回测系统与实盘系统之间的对账应当能捕捉流水线分歧。当实盘系统对相同输入给出不同输出时，原因就是一个待修复的 bug。

### 绩效衰减导致的统计性失效

*统计性*失效发生时，系统完全按设计运转（相同输入产生相同输出），但输出已不再能预测收益。实现没有问题；是模型衰减了。

统计性衰减有四种成因：

- *过拟合*：模型从训练数据中学到的模式无法泛化到新数据。回测业绩反映的是样本内噪声，而非样本外信号。每个策略都有这种风险；验证能缓解，但不能消除。Harvey, Liu, and Zhu (2016) 展示了多重假设检验如何在整金融研究中推高回测业绩，同样的风险也适用于单个策略的开发。
- *前视偏差*：细微的信息泄露抬高了回测结果。也许特征在计算时用了实时情况下拿不到的未来数据；也许幸存者偏差把已退市证券从标的池中剔除了。
- *市场状态变化*：市场结构变了。波动率状态改变、相关性破裂，或特征与收益的关系发生了演化。训练期内有效的做法，在当前市场中不再有效。
- *alpha 衰减*：策略变得拥挤。其他参与者——人或算法——发现了相似的模式。被捕获的 alpha 引来了竞争，收益被套利抹平。McLean and Pontiff (2016) 提供了实证记录：异常现象一旦公开，其盈利能力便急剧下降，与数据挖掘偏差和公开发布后套利的混合解释相一致。

### 为什么这一区分至关重要

不同的失效需要不同的响应：

| 失效类型 | 诊断 | 响应 |
| --- | --- | --- |
| 技术性 | 相同输入 → 不同输出 | 修复 bug |
| 统计性 | 相同输入 → 相同输出 → 收益不佳 | 再训练、重新设计或退役 |

*表 26.1：按失效类型给出的响应*

把统计性衰减当作 bug，只会带来徒劳的调试；把 bug 当作统计性衰减，则会导致不必要的模型改动。任何调查的第一步，都是判定失效属于哪一类。

Capponi et al. (2025) 对非平稳性如何侵蚀模型可靠性做了形式化处理：问题不是绩效会不会退化，而是何时退化，以及检测能否及时到位、让响应来得及。接下来各节的监控框架假定衰减必然发生，并据此构建系统化的检测。

## 26.2 绩效监控

系统化的监控框架要跟踪多个绩效维度，把实盘结果与回测预期相比较，并在指标越过有意义的阈值时触发告警。目标是尽早发现衰减，赶在损失累积之前做出响应。

### 数据完整性门禁

在监控模型绩效之前，先校验喂给它的数据。实盘中相当一部分表面上的漂移事件其实是隐蔽数据缺陷：价格过期、公司行为处理不当、关联断裂、时区错位、bar 缺失或行重复。按 *26.1 节*的分类，它们属于技术性失效，但最先表现出来的却是下游指标中的统计异常。一层轻量的数据契约（data contract）能在接入阶段就拦住这些缺陷，不让它们蔓延到特征计算、推理或执行环节。Pandera 这类模式校验库会对每个传入的 DataFrame 强制执行类型约束、空值边界、时间戳单调排序和唯一键。Great Expectations 提供类似的方法，其校验产物可读性强，便于团队协作。

关键的设计选择是，对执行关键的数据源采取*故障关闭*（fail-closed）策略：市场数据未通过校验，就不要据其交易。非关键的分析流水线则可以故障开放（fail open），只发警告。把校验结果接入下文同一套分级告警系统：主数据源上的模式违规应触发严重告警，次要数据源上的轻微异常则只需观察级通知。

### 滚动指标框架

时点指标会掩盖趋势。整体夏普比率尚可的策略，近期窗口可能已在急剧衰减。滚动计算能揭示总量统计所遮蔽的细节。对截至时刻 t、长度为 w 个交易日的滚动窗口，基本监控公式如下：

Ŝ(t, w) = √252 · r̄(t−w+1…t) / s(t−w+1…t)

H(t, w) = (1/w) · Σᵢ 1(rᵢ > 0)，i 从 t−w+1 取到 t

DD(t) = 1 − Vₜ / max(Vᵤ : u ≤ t)

其中 r̄ 为扣除成本后的日均策略收益，s 为其样本标准差，Vₜ 为组合价值，H 为命中率。这些只是简单的诊断量，不是充分统计量；关键在于始终如一地在实盘扣费后收益上计算它们，并与验证阶段的同口径数值比较。以下关键指标在前几章已有介绍。

#### 滚动夏普比率

在滚动窗口（例如 30、60、90 日）上计算夏普比率，并与回测预期并列绘图。回测夏普与实际夏普之间的差距，往往就是关键的监控指标。

标定良好的策略，其实盘夏普应落在回测夏普附近的合理区间内（考虑估计不确定性）。持续跑输（实盘夏普持续比预期低 0.5 或更多）意味着回测过拟合，或者市场状态发生了变化。

#### 信息系数

预测值与随后收益之间的相关性。夏普衡量的是总体绩效，IC 衡量的则是信号层面的预测精度。

跟踪滚动 IC，在预测衰减完全体现到收益之前就把它抓住。即使 IC 在下滑，策略也可能因行情有利而暂时维持可接受的收益。一旦行情恢复正常，退化的预测就会带来亏损。

#### 命中率与盈亏比

命中率与盈亏比回答的问题是：多大比例的交易盈利？盈利时赚多少？亏损时亏多少？这两个指标把夏普分解成可解释的组成部分。

命中率下降而盈亏比稳定，说明模型的方向性预测在变弱；命中率稳定而盈亏比恶化，说明方向判断正确，但幅度估计不佳或执行在变差。

#### 回撤深度与持续时间

最大回撤衡量从峰到谷的最大跌幅，回撤持续时间衡量修复需要多久。

回撤在深度与时间上都超出历史常态（比回测中观察到的更深、更久），说明策略已进入陌生领域。模型可能正在它从未训练过的市场状态下运行。

### 告警阈值

监控持续产生数据，告警则需要阈值。阈值太紧会产生噪声和告警疲劳；阈值太松则会在发现之前就放任损失发生。

采用分级阈值设计：

- **观察**（黄色）：指标偏离正常区间但尚不令人担忧。记录备查，无需行动。示例：预期值为 1.5 时，滚动 30 日夏普比率跌破 1.0。
- **警告**（橙色）：指标显著恶化。立即调查，考虑降低敞口。示例：滚动夏普连续两周低于 0.5。
- **严重**（红色）：指标突破硬性限额。采取保护性行动，可能触发自动化响应。示例：滚动夏普连续 30 天以上为负，或回撤超过历史最大值。

用回测数据经验性地校准阈值：历史上每次绩效退化之前，指标处于什么水平？什么数值本可以给出足够预警，让你来得及行动？

阈值设计还必须防止告警疲劳。天天骚扰团队的监控系统，只会训练大家无视它。只保留有明确对应动作的告警，用历史数据度量误报率，并在新增指标时复查告警阈值。如果某个阈值频繁触发却从未改变过敞口、再训练节奏或诊断优先级，那它就是披着严谨外衣的噪声。

### 可视化仪表盘

生产级监控仪表盘应展示五个面板，无论它是用 Grafana 配 Prometheus 后端搭建，还是用 Streamlit 这类更简单的技术栈对着平面文件搭建：

- **实时盈亏（PnL）**：相对基准的累计与每日收益，并叠加回测曲线，展示预期净值对实际净值。
- **滚动指标**：30、60、90 日窗口上的夏普、IC 与命中率。多窗口可以区分暂时性噪声（短窗口下跌、长窗口稳定）与持续性衰减（所有窗口同步下行）。
- **回撤跟踪器**：当前深度与持续时间的时序图，用水平线标出历史最大值与熔断阈值。
- **告警状态**：颜色编码的指示（绿/黄/橙/红）与最近一次状态变化的时间戳。一眼即可看清系统健康状况。
- **回测对比**：实盘净值叠加在回测净值曲线上：两条线之间的差距是核心的直观诊断。

### 与回测预期的比较

回测给出你的绩效假设，实盘交易检验这个假设。系统化的对比能揭示现实是否符合预期。对每个指标，跟踪：

- **回测值**：验证阶段给出的预期是多少？
- **实盘值**：实际观察到的是什么？
- **偏差**：两者相差多远？
- **显著性**：偏差是否超出了估计噪声所能解释的范围？

偏差在所难免，因为回测估计本身带有置信区间。但持续朝一个方向的大幅偏差，说明有系统性的东西变了。

对关键指标计算回测-实盘比率。回测夏普 2.0、实盘夏普 1.5 的策略，实现比率为 0.75。持续跟踪这个比率。实现比率不断下降（即使绝对绩效仍可接受）说明绩效在持续退化。

### 执行质量监控

模型绩效指标捕捉的是信号质量，但*执行质量*往往主导短周期 PnL 的波动，还可能伪装成模型衰减。点差扩大、成交率下降、滑点增加或券商限流，都会在模型预测不变的情况下侵蚀实际收益。

把执行与模型指标放在一起监控：相对回测假设的滑点、实付点差相对报价点差、成交率与部分成交行为，以及从信号生成到订单成交的延迟分布。计算一个实际-模拟交易成本比率，类似上文提到的回测实现比率。如果执行成本持续高于回测假设，问题就出在市场微观结构或基础设施，而不是模型——此时再训练是错误的响应。

## 26.3 漂移检测

绩效监控告诉你*有东西变了*，漂移检测告诉你*变的是什么*。通过跟踪输入分布、特征重要性和特征-目标关系的变化，你可以在衰减完全体现到收益之前做出诊断。

### 输入分布变化导致的数据漂移

**数据漂移**指输入特征的统计性质偏离其训练分布。模型接收到了训练时没有见过的数据。

**群体稳定性指数**（Population Stability Index，**PSI**）量化这种分布偏移：PSI = Σᵢ (Aᵢ − Eᵢ) · ln(Aᵢ / Eᵢ)，其中 Aᵢ 是分箱 i 中的实际占比，Eᵢ 是训练阶段该分箱的期望占比。常用的经验解读是：

- **PSI** < 0.1：无显著偏移，模型输入保持稳定
- **PSI** > 0.25：显著偏移，模型预测很可能不可靠
- **PSI 0.1–0.25**：中等偏移，需要调查，但模型尚未失效

对每个关键特征，将近期生产数据与训练参照集比较来计算 PSI。PSI 的飙升往往先于绩效退化出现，因此能在收益恶化之前发出预警。本章 notebook 直接在 `us_equities_panel` 特征产物上完成这一计算，把最后一个可得的留出期预测年份与先前的参照窗口进行对比。

**柯尔莫哥洛夫-斯米尔诺夫检验**（**K-S 检验**）弥补了 PSI 在连续特征上的不足，它度量累积分布函数之间的最大距离。与 PSI 不同，K-S 检验不依赖分箱假设，直接检验两个样本是否来自同一分布，因此对连续特征而言是首选——分箱只会丢掉信息。

### 重要性变化导致的特征漂移

即使输入分布保持稳定，特征的*重要性*也可能改变。历史上驱动预测的特征可能影响力下降，其他特征则变得突出。SHAP 值监控 (Lundberg and Lee, 2017) 把预测分解为可加的归因并在实盘窗口上汇总，从而跟踪每个特征的贡献随时间的变化。有三个汇总量值得关注：SHAP 平均绝对值（贡献的平均幅度）、SHAP 方差（贡献的稳定性）和相对排名（重要性层级是否变动）。排名持续变化，加上某个核心特征的贡献崩塌，是模型的预警信号——它正依赖一段市场已不再回报的关系。*26.2 节*介绍了这些汇总量如何与绩效指标一起呈现在运维漂移仪表盘中。

### 关系变化导致的概念漂移

最隐蔽的漂移来自特征与目标之间关系的变化。输入看起来相似，却不再以同样的方式预测结果。这就是**概念漂移**：底层数据生成过程变了。Lu et al. (2018) 给出了概念漂移类型的分类（突变、渐变、增量、循环重现），每一类都需要不同的检测与适应策略。Hinder, Vaquet, and Hammer (2023) 综述了漂移检测的最新进展，把 ADWIN 和 DDM 放入更广的方法分类中，并讨论其运维上的取舍。市场状态转换是概念漂移的典型例子：当市场从趋势行情转向均值回归，此前预测正收益的同一条动量信号现在预测的是负收益。特征分布可能没有变化，但特征-目标关系已经反转。

生产团队常依赖 `river` 这类在线漂移库来实时监控概念漂移。本章 notebook 在留存的验证误差流上使用轻量的检测器逻辑，以保持告警行为的透明可控。

**自适应窗口**（Adaptive Windowing，**ADWIN**）(Bifet and Gavaldà, 2007) 维护一个长度可变的观测窗口，持续检验近期观测与更早观测是否存在统计差异。一旦检测到漂移，窗口就收缩到只包含漂移之后的数据。

把 ADWIN 应用于策略的预测误差，即预测收益与实际收益之差。如果误差分布发生显著变化，说明预测问题本身发生了变化。

**漂移检测方法**（Drift Detection Method，**DDM**）(Gama et al., 2004) 监控误差率随时间的变化。它维护误差率和标准差的滚动统计量：误差率中度上升时发出警告，大幅上升时发出漂移告警。

DDM 比 ADWIN 更简单但适应性更差，在计算开销构成硬约束时是一个轻量替代。在线漂移 notebook 在封存的留出期之前的最后一个真实验证年份上比较 ADWIN 风格与 DDM 的行为，把告警聚集与市场压力代理变量（而非合成变点）相关联。

### 实践工作流

不是所有东西都需要监控。重点关注：

- **高重要性特征**：历史上 SHAP 贡献较大的特征。它们一旦漂移，模型绩效大概率跟着下滑。
- **高波动特征**：历史上分布多变的特征。它们更容易漂移。
- **领域敏感特征**：已知会随市场状态变化的特征：波动率度量、相关性指标、流动性指标。
- **监控频率**：在响应速度与噪声之间取得平衡。*表 26.2* 总结了一套实用的频率安排，把每日检查与更慢、计算开销更大的诊断区分开来。

| 方法 | 频率 | 典型触发条件 |
| --- | --- | --- |
| 对关键生产特征计算 PSI | 每日 | 高重要性输入的 PSI > 0.25 |
| 连续特征的 K-S 检验 | 每日或每周 | 近期样本相对参照样本的 p 值 < 0.05 |
| SHAP 重要性监控 | 每周 | 排名重排，或核心特征的 SHAP 平均绝对值大幅下降 |
| 对预测误差运行 ADWIN/DDM | 持续 | 实盘误差流出现警告或漂移状态 |

*表 26.2：关键监控方法*

告警集成：把漂移检测接入你的告警系统。关键特征的 PSI 超过 0.25 应触发调查；ADWIN 的漂移信号应升级为警告状态。

检测器本身也需要被监控。在线漂移 notebook 跟踪告警频率、警告连续触发次数及相关健康信号，以便在 ADWIN 或 DDM 的误报淹没运维人员之前重新校准其灵敏度。像对待其他生产指标一样对待检测器健康度：如果它不断呼叫却从未改变任何决策，它就已经没用了。

### 从检测到诊断

漂移检测告诉你有东西变了；诊断告诉你这变故要不要紧：

| 检测到漂移？ | 绩效衰减？ | 解读 | 响应 |
| --- | --- | --- | --- |
| 是 | 否 | 模型稳健；分布已偏移，但关系依然成立 | 持续监控，无需行动 |
| 否 | 是 | 漂移覆盖不全，或属渐进式概念漂移 | 扩大监控范围，检查未被跟踪的特征 |
| 是 | 是 | 特征漂移可解释衰减 | 用近期数据再训练，或改用针对特定市场状态的模型 |
| 否 | 否 | 运行健康 | 继续常规监控 |

*表 26.3：漂移检测的响应*

诊断工作流是：检测漂移，与绩效关联，提出机制假设，再用有针对性的分析加以验证。这套系统化方法同时防止反应不足（无视真实问题）与反应过度（因噪声而改动模型）。

检测与诊断回答了模型何时衰减、为何衰减；下一节讨论*该怎么办*：既保护资本、又允许模型演进的安全模型更新。

## 26.4 安全的模型更新

监控发现了衰减，诊断找到了原因。现在必须更新模型，同时又不能拿一个失效去换另一个失效——替换者可能比衰减的原模型表现更差。安全的更新工作流在允许模型演进的同时保护资本。

### 何时再训练

有两种基本做法：

- **定期再训练**：按固定间隔更新模型——每周、每月或每季度。周期应反映策略的预期衰减速度。在快速变化的市场中运作的高频策略可能需要每周更新；长期策略可能每季度再训练一次。
- **触发式再训练**：在监控信号表明必要时更新模型。当滚动夏普跌破阈值、PSI 越过限额，或 ADWIN 发出漂移信号时，触发再训练流水线。

定期再训练的好处是可预期，但可能做了不必要的更新（一切未变时），也可能更新太迟（衰减加速时）。触发式再训练响应实际状况，但需要稳健的监控来避免误触发。两者可以结合：以定期为基线，以触发应对特殊情况。

### 影子模式评估

任何新模型在触碰资金之前，先以**影子模式**运行：处理实盘数据、生成预测，但不交易。影子模式提供了贴近真实环境的验证。我们在 `ml4t-live` 中直接实现了这一机制：策略对着实时数据运行，同时由一个虚拟组合记录假想持仓与 PnL。本章 notebook 用真实的 `us_equities_panel` 产物重建了这一逻辑：先从历史验证记录中选出现任模型，再在下一个发布年份的数据上回放影子窗口，并在任何加仓之前记录候选模型的假想结果。

把新模型（**候选模型**）与生产模型（**现任模型**）并列部署。两者接收完全相同的实时数据流并实时生成预测，但只有现任模型执行交易。三个对比指标支撑决策：

- **预测一致性**：现任与候选在方向上一致的频率。不一致未必是坏事，但在晋级之前应当弄清不一致的来源。
- **假想收益**：候选模型若实际交易本可获得的收益，按贴近现实的执行假设计算。
- **风险特征**：候选承担的风险与现任是相似还是不同。风险画像的意外变化值得调查。

#### 影子期时长

影子期应覆盖足够多样的市场环境，以检验稳健性。在趋势行情中表现更好的候选，到了震荡行情可能失灵。常见的默认值是 60 天影子期（既足以覆盖多种市场状态，又不至于拖慢部署节奏），但合适的窗口长度取决于策略的**调仓频率**：月度策略至少需要两个调仓周期的影子运行。

#### 统计检验

仅凭肉眼观察绩效是不够的。统计检验用于判断候选是真优胜，还是观测到的差异只是噪声。对日收益差做配对检验，可以确定候选在同一批日期上是否具有更高的平均收益；而夏普比率的比较需要能同时考虑均值与波动率以及两条收益序列之间相关性的方法。经典检验比较夏普比率之差：如果 Ŝ_C − Ŝ_P 是观测到的差值，其标准误决定了这个差距是否具有统计意义。最早的 **Jobson-Korkie 检验**为这类比较提供了早期框架，但它依赖"收益独立同分布且服从正态分布"的严格假设；后续的修正与稳健替代方法放宽了其中部分假设。Bailey and López de Prado (2014) 提出**缩减夏普比率**（deflated Sharpe ratio），当候选是多次实验筛选后的产物时尤其有用，因为它对估计误差、多重检验和非正态收益做了调整。

**自助法（bootstrap）**提供了实用的替代方案。对成对的收益观测进行重采样（收益存在序列相关时用块自助法），然后对每个样本计算夏普比率之差。所得分布给出置信区间，也给出候选的表面优势有多大比例纯属偶然的经验估计。

#### 效应量同样重要

统计显著的 0.05 夏普提升未必值得冒部署风险。为晋级设定一个最小效应量（例如夏普提升 0.2–0.3），低于该值时无论统计显著性如何都不晋级。

**统计功效与检验本身同样重要**。短的影子窗口既无法确认也无法有把握地否定小幅改进，尤其在收益噪声大、自相关或厚尾时。López de Prado, Lipton, and Zoonekynd (2025) 说明了为什么短样本上的朴素夏普比较不稳定，并量化了在给定效应量下做出可靠推断所需的观测数量。如果你关心的效应量很小，就延长影子期，或先做基于自助法的功效分析，再宣布候选更优。

### 分阶段上线

影子模式验证通过后，也不要立即替换现任模型。分阶段过渡：

- **资金封顶的 A/B 测试**：把一小部分资金（例如 5% 到 10%）分配给候选模型。系统从此度量的是真实绩效，包括执行成本、滑点和市场冲击。现任模型继续交易其余资金。真金白银的 A/B 测试能暴露影子模式发现不了的问题：候选的信号可能集中在流动性差的股票上，或者其仓位规模可能造成市场冲击。这些效应只有在资金实际部署时才会显现。
- **逐步提高**：如果 A/B 结果验证通过，就按 10% 到 25%、25% 到 50%、50% 到 100% 这样的门禁逐级提高候选的配置，每一级都要求最短观察期，且持续跑赢之后才能晋级下一级。完整的过渡通常持续 60 到 90 天，取决于调仓频率与市场状况。
- **晋级标准**：定义明确的阈值，而不是依赖主观判断。一套示例标准要求：候选的夏普比率至少比现任高 0.2，且在 10% 水平上统计显著，并且任何阶段都未出现超过策略历史最大值的回撤。这些数值只是经验起点，应按策略的换手率和信号噪声加以校准。

### 回滚流程

每次部署都应可回退。晋级新模型之前：

- **归档现任模型**：以完整的版本管理保存当前生产模型，确保可以即刻恢复。
- **定义回滚触发条件**：明确哪些条件触发自动回滚，例如回撤超过阈值、连续亏损日或系统错误。
- **测试回滚机制**：部署候选之前，验证回滚真的可用。理论上可行的回滚流程在压力下失灵，等于没有。
- **在自动回滚与手动回滚之间做抉择**：低层触发条件（系统错误、数据源故障）应当自动回滚——此时速度比精细更重要；高层触发条件（绩效退化）可能需要人工确认，以避免对噪声反应过度。

`06_mlflow_experiments` 补充了系统化管理这些晋级决策所需的实验排序、产物记录和注册表工作流。

安全更新应对的是渐进式衰减；下一节讨论突发失效：熔断机制在亏损或基础设施状况突破硬性限额时自动停止交易——赶在人工复核来得及介入之前。

## 26.5 熔断机制与安全

监控与安全更新应对渐进式衰减，熔断机制应对突发失效：灾难性错误发生、速度比精细更重要的时刻。它们是你的自动化安全网：简单而硬编码的规则，在复杂系统失灵时保护资本。

### 多层级保护

纵深防御：多道相互独立的安全层，各自拦截不同的失效模式。熔断机制架构实现了四个层级：

- *单笔交易*（单笔订单校验）
- *单策略*（单一策略的敞口限额）
- *组合*（所有策略的总体风险）
- *系统*（基础设施健康与延迟监控）

每一层都独立运行：任何一层被突破，都会就地停止相应范围的操作，无需更高层级介入。*图 26.4* 展示了这一分层防御架构。

![图 26.4](assets/figure_26_4.png)

*图 26.4：熔断机制架构。单笔交易、策略、组合与系统各层提供独立的失效遏制*

最重要的是三类熔断器。

#### 基于亏损的熔断器

最重要的类别：亏损超过阈值即停止交易：

- 单日回撤限额（例如 -2%）：防范单日灾难
- 单周回撤限额（例如 -5%）：拦截持续失血
- 自峰值最大回撤（例如 -10% 至 -15%）：终极熔断

基于回撤的规则在组合管理中历史悠久 (Korn, Möller, and Schwehm, 2022)，但需要仔细校准。Varma (2025) 认为，固定的回撤截断线是钝器，因此回撤熔断器与敞口、流动性、市场压力等其他信号结合使用效果最好。当亏损突破真正的硬性限额时，立即停止交易。不要等人工复核。不要试图靠继续交易来填坑。先止血。

#### 基于持仓的熔断器

这类机制防止危险的集中：

- 单一资产最大仓位（例如组合的 5%）
- 单一板块最大敞口（例如任何板块不超过 20%）
- 最大相关性（避免多个持仓同涨同跌）

持仓限额捕捉的是模型对特定下注过度自信的情形。即使每笔交易单独看都合理，汇总敞口也可能已经危险。

#### 基于异常的熔断器

这类熔断器响应异常市场状况：

- 极端波动（例如 VIX > 40）
- 流动性枯竭（例如买卖价差达到正常水平的 3 倍）
- 价格错位（例如任何资产日内波动超过 10%）

市场承压时，正常关系失效。在正常条件下训练的模型，在极端条件下可能输出荒谬结果。异常期间先离场观望，往往是审慎的做法。

Notebook `04_circuit_breakers` 实现了回撤、日亏损、连续亏损和延迟四类熔断器；上文基于持仓与基于异常的类别，则是用不同的触发条件扩展同一状态机。

**上文的交易熔断器是风险控制**：基于 PnL、持仓或市场状况决定何时停止交易的规则。下文描述的软件熔断器模式目的不同：**基础设施韧性**。它在系统依赖（数据源、执行 API）变得不可靠时防止级联失效。两者都必不可少，防范的是不同的失效模式。

### 实现模式与库

Notebook 实现了自定义的熔断器状态机，让控制逻辑一目了然。在生产中，`pybreaker` 之类的库可以为基础设施依赖提供同样的 CLOSED/OPEN/HALF_OPEN 生命周期，而不改变底层策略设计。

熔断器在三种状态间运转：

- **Closed**（闭合，正常）：调用直接穿透到底层函数，熔断器统计失败次数。
- **Open**（断开，已触发）：失败次数超过阈值（例如连续 5 次失败）后，所有调用立即失败、不再执行。这避免把资源浪费在已知损坏的依赖上。
- **Half-open**（半开，试探）：超时期（例如 30 秒）过后，熔断器放行一次调用。成功则回到 Closed 状态；失败则重新断开。

这个三态模型防止级联失效。数据源宕机时，你不会希望每个预测请求都在等待数据中超时。熔断器快速失败，既节省系统资源，也避免产生僵尸进程。

无论用自定义实现还是 `pybreaker`，每一次 CLOSED→OPEN 转换都应触发告警，每一次 OPEN→HALF_OPEN→CLOSED 恢复都应记录在案，供事后复盘。这些事件构成熔断器监控仪表盘的基础。

系统级监控在基础设施退化时停止交易。典型的 100ms 端到端延迟阈值，能在数据源延迟、执行系统变慢或网络问题引发"用过期数据交易"之前把它们抓住。延迟一旦超过阈值，熔断器断开，交易暂停，直至系统恢复。

### 恢复流程

触发熔断只是开始，不是结束。你需要清晰的恢复规程，分为即时响应、排查问题和恢复交易三步。

**即时动作**：

1. **确认告警**，通过 PagerDuty、Slack 或你们使用的任何平台。
2. **评估形势**：是什么触发了熔断器？当前敞口多大？
3. **守住头寸**：若仍有部分敞口，决定平仓还是对冲。

**诊断问题**：

- 这是技术性故障（数据源、执行系统）还是模型故障（预测错误）？
- 市场是否正处于触发异常熔断器的非常规状况？
- 导致触发的事件序列是什么？

**恢复标准**：

明确恢复交易前必须满足的条件：

- 所有系统组件健康
- 数据源通过校验
- 市场状况恢复正常（若由异常触发）
- 根因已查明，且已被修复或确认无害

**渐进重启**：

不要立即满负荷恢复。先以缩小的仓位规模或模拟盘起步，确认系统行为正常后再逐步放大。

### 人工接管的考量

熔断器应当自动化：故障发生时速度就是一切。但授权人员也应当能够接管（override），以应对熔断器误触发的情形。

接管纪律要求：记录每一次接管（谁、何时、为何），要求明确的风险确认，为接管设定时限（例如一小时，除非续期），并在事后复查所有接管。接管过于容易，熔断就形同虚设；完全禁止接管，则无法纠正真正的误报。平衡点取决于你的风险容忍度与运维成熟度。

有了监控、漂移检测、安全更新和自动化安全，下一节概述配套的 MLOps 基础设施（特征存储、模型注册表和 CI/CD）——生产部署中，上述治理层都依赖它们。

**实现**：`04_circuit_breakers` 演示自定义熔断器状态机、分层安全规则和恢复流程。

## 26.6 MLOps 基础设施概览

前面几节聚焦于监控与安全——生产治理中最关键的部分。配套的基础设施工具有用但并非核心；小团队可以从最少的基础设施起步，随需求增长再逐步增加复杂度。

### 用特征存储防止训练-服务偏斜

**特征存储**（feature store）确保训练阶段计算的特征与推理阶段计算的特征完全一致。没有这种一致性，实盘系统收到的输入就会与回测不同——这是一颗迟早会引爆的技术性失效地雷。

核心问题在于：研究阶段你可以完全自由地从历史数据计算特征；生产阶段则必须从流式数据、在严格的延迟约束下实时计算同样的特征。细微差异（日期处理、归一化窗口、缺失数据的默认值）会造成训练-服务偏斜（training-serving skew），悄无声息地拉低绩效。Sculley et al. (2015) 记录了这类"隐性技术债务"如何在各 ML 系统中层层累积，使特征一致性成为第一优先级的关注点。Paleyes, Urma, and Lawrence (2023) 综述了各行业的部署挑战，指出数据质量、监控与系统集成是反复出现的运维瓶颈，进一步印证了在特征存储与漂移检测上早做投入的必要。

**Feast**（`feast.dev`）提供统一的特征注册表。特征只需定义一次，Feast 同时负责历史取数（用于训练）与在线服务（用于推理）。主要好处：

- **一致性**：同一份特征定义同时服务于训练与生产
- **时点正确性**：Feast 管理时间连接，防止前视偏差
- **版本控制**：特征定义与模型一同版本化

Feast 区分**离线**存储与**在线**存储。离线存储（通常是 Parquet、BigQuery 或 Redshift）保存用于训练的历史特征值，可能是跨数千个实体的多年数据。在线存储（Redis、DynamoDB）只保存最新的特征值，用于低延迟推理。Feast 自动把特征从离线物化到在线，确保训练与服务之间的一致。

对交易系统而言，这一架构解决了一个常见问题：回测时你用 pandas 借助完整的事后信息计算滚动特征（20 日波动率、60 日动量）；生产中则必须随着新数据到来增量计算同样的特征。Feast 的特征定义保证计算完全一致；在线存储保证服务延迟保持在毫秒级以内。

特征存储可以从小型实验（几个标的、几个特征）一直扩展到跨大标的池、数千个特征的生产部署。我们的 notebook 直接在真实的 `us_equities_panel` 特征表上展示控制逻辑：基于存储的 Parquet 数据源定义特征视图（feature view），为训练执行时点正确的离线连接，为推理重建在线风格的 as-of 快照，并度量一条错误时间戳规则造成的偏斜。核心概念始终是训练-服务一致性，而不是某个具体的供应商配置。

### 数据版本控制与血缘

特征存储保证训练与服务的一致，但回答不了这个问题：*究竟是哪个数据集训练出了这个模型？*当模型在生产中失效，你需要区分数据损坏与真实的市场状态转换时，必须能够精确复现训练数据。没有数据版本控制，诊断只能靠猜，回滚则风险重重。

至少，每次训练运行都应记录一份*运行清单*（run manifest）：一个 JSON 产物，登记 git 提交哈希、数据集快照标识（内容哈希或分区版本）、特征集版本、模型注册表版本和配置哈希。DVC（`dvc.org`）提供类 Git 的接口，把大型数据与模型文件同代码一起版本化，让小团队无需专门的元数据平台也能实现可复现与回滚。把清单作为带标签的产物挂到每个 MLflow run 上，任何已部署模型都能追溯回其确切输入。

### 模型注册表与实验跟踪

**模型注册表**为模型提供版本控制：跟踪哪个模型版本已部署、用了什么训练数据、在测试中表现如何。

**MLflow**（`mlflow.org`）提供了一个轻量方案，集三者于一体：

- **实验跟踪**：为每次训练运行记录超参数、指标和产物
- **模型版本控制**：保存训练好的模型及其完整血缘（包括训练数据、代码版本、依赖）
- **部署阶段管理**：管理从"Staging"到"Production"状态的流转

对于 *26.4 节*所述的安全更新工作流，MLflow 跟踪哪个模型是现任、哪个是影子模式中的候选，以及两者的绩效对比。训练期间，MLflow 自动记录 IC、夏普等指标。这些记录在案的指标成为晋级时为候选排序的依据。

模型注册表还支撑可审计性。当监管者或风险官问起"模型为什么做出这个决定？"，你必须能确切说出部署的是哪个模型版本、何时部署、用什么数据训练、超参数是什么。CRISP-ML(Q) 框架 (Studer et al., 2021) 与美联储关于模型风险管理的 SR 11-7 指引 (Board of Governors, 2011) 都把模型血缘与可复现性列为监管上的必然要求。

注册表条目只是治理记录的一部分。生产团队还需要可留存的评审材料：总结预期用途与已知局限的模型卡（model card）、独立验证备忘录，以及展示实盘绩效、漂移状态和未决事件的最新监控报告。Notebook 展示了与之配套的 MLflow 环节——产物记录、实验汇总和注册表阶段——但这些记录替代不了治理材料本身。如果这些材料只存在于聊天记录或临时拼凑的仪表盘里，SR 11-7 的核心要求（有效挑战、持续监控、成文的治理）就很难满足。

### 面向交易模型的 CI/CD

**持续集成/持续部署（CI/CD）**应用于 ML 时有特殊考量。标准 CI/CD 包括：特征计算与信号生成的单元测试、流水线组件的集成测试、确认模型绩效超过最低阈值的验证测试，以及部署后的冒烟测试。ML 特有的补充是自动化部署门禁：除非验证指标通过、影子模式对比显示无回归且回滚已经核实，否则任何模型都不得进入生产。GitHub Actions、GitLab CI 或类似工具负责编排这些检查，无需任何人记得去手动跑验证。

### 技术栈的适度规模

不是每个团队都需要企业级基础设施。合理的演进路径：

**最小配置（单人或小团队）：**

- 用 pandas/numpy 计算特征，辅以细致的文档
- 模型存入带版本的目录（大文件用 Git LFS）
- 用 cron 或 systemd 定时器跑定时流水线
- 按检查清单手动部署
- 用简单仪表盘监控（Streamlit、基础 Grafana）

**中级配置（成长中的团队）：**

- 用 Feast 保证特征一致性
- 用 MLflow 做实验跟踪、DVC 做数据版本控制
- 用 Prefect（`prefect.io`）或 Dagster（`dagster.io`）做工作流编排，带重试与可观测性
- 用 GitHub Actions 做自动化测试
- 用 Prometheus 和 Grafana 做监控
- 带一致关联 ID（run、strategy、order）的结构化日志，便于事故诊断

Prometheus-Grafana 组合是标准的可观测性搭配：Prometheus 以 15–30 秒的间隔抓取自定义交易指标（`strategy_sharpe_30d`、`signal_ic_rolling`），Alertmanager 按可配置的升级策略把阈值突破路由到 Slack 或 PagerDuty。

**成熟配置（规模化生产）：**

- 具备实时服务能力的全功能特征存储
- 带审批工作流的模型注册表
- 用 Kubernetes 做部署编排
- 用 OpenTelemetry（`opentelemetry.io`）在整个信号到执行的流水线上关联日志、指标与追踪

起步时比自己以为所需要的更简单一些。基础设施服务于交易系统，而不是相反。监控（*26.2–26.3 节*）与安全（*26.5 节*）两节比工具选型更重要。先把它们做对，再按约束需要优化基础设施。**实现**：

- `05_feast_feature_store` 通过真实的案例研究特征表演示特征存储概念、时点正确的连接与特征血缘。
- `05b_feast_live` 把同一工作流扩展为通过实时 Feast 集成使用相同的产物。
- `06_mlflow_experiments` 通过本地 SQLite 注册表和内容寻址的运行包演示实验跟踪、产物记录和注册表式晋级工作流。

以下小结把检测、响应与安全三个层次汇拢为三层治理模型——它让已部署的交易系统保持正确运转，或者在无法保持时体面失效。

## 26.7 本章小结

我们构建了把生产级交易系统与研究原型区分开来的部署后基础设施。核心洞见在于诊断：技术性失效（产出错误输出的流水线 bug）与统计性失效（输出正确却不再预测收益）需要不同的响应。混为一谈只会浪费时间和资本。

三层治理模型从检测到响应再到自动化安全。检测从数据质量门禁开始，经由滚动绩效指标、执行质量监控和漂移诊断展开，后者把输入偏移（PSI、K-S）、特征重要性变化（SHAP）与概念漂移（ADWIN、DDM）区分开来。响应借助影子模式、资金封顶的 A/B 测试和分阶段上线来替换衰减的模型，而不是用一个失效换另一个失效。自动化安全是最后防线：多级熔断机制在亏损、敞口或基础设施状况突破硬性限额时停止交易。配套的 MLOps 基础设施（*26.6 节*）——涵盖特征存储、数据版本控制、模型注册表与工作流编排——应按运维成熟度适度配置，而非全盘照搬。

*第27章*将从实现退后一步，反思当整条流水线（从数据到建模、部署与治理）作为一个连贯、持续验证的系统运转时，会产生怎样的系统化优势。
